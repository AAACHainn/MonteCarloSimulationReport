# 趋势线与历史交易回放卡顿：排查与修改方案

2026-10-18，按功能提交 `8efb49b` 检查。本文为待实施方案，未修改应用逻辑、绘图记录、数据库驱动或日志模式，未重启服务。

2026-10-19 更新：下文保留排查时的调用路径。普通回放和所有历史页现已统一按会话读取、保存后端绘图；所有历史页已移除绘图草稿的浏览器存储逻辑，直接忽略旧草稿，不再合并本地副本；当前存储和删除规则见[归档绘图持久化](archived-drawings.md)。

## 已确认的调用路径

- [历史交易回放](../components/market-replay/historical-replay-client.tsx) 读取当前会话的绘图，与历史页本地绘图合并后，传给同一个 `ReplayChart`。`readOnly` 只限制交易操作，没有切断绘图投影路径；没有发现跨会话混读是本次卡顿的必要条件。
- [图表组件](../components/market-replay/replay-chart.tsx) 的 `syncDrawingPrimitive` 把 `barsRef.current` 传给趋势线与斐波那契；该引用指向隐藏边界之前的 `visibleBars`。K 线主序列却通过 whitespace 保留完整已加载时间轴。因此，隐藏后投影所用的时间轴与实际图表轴不一致，原本已加载的端点会被当作窗口外端点。
- [趋势线 primitive](../lib/market-replay/trend-line-primitive.ts) 的 `updateAllViews` 每次重算所有绘图的两个端点。[斐波那契 primitive](../lib/market-replay/fibonacci-retracement-primitive.ts) 使用相同的定位函数，也受影响。
- [端点定位](../lib/market-replay/chart-drawings.ts) 的 `logicalIndexForSessionTimestamp` 对窗口外的纯时间端点逐桶调用 `getAdjacentAggregationBucketStart` 和 `getAggregationBucket`，循环上限为 100,000。桶计算涉及交易时段、周末、时区和夏令时；重绘时没有复用端点的时间轴位置。窗口内源序号查找及若干时间查找还使用线性扫描。
- `sourceSequence=null` 是在空白区画线时产生的合法状态，不代表绘图损坏。不能删除这些绘图，或编造源序号来规避问题。

## 本机只读复现

读取本机 ES「模拟训练」会话：19 条趋势线、38 个端点，其中 3 个仅有时间、没有源序号。源周期 1 分钟，显示周期 5 分钟，RTH。读取最多 24,000 根源行情，在内存聚合后构造 1,200 根历史窗口；隐藏场景使用前 65% 的 780 根作为 primitive 当前输入，模拟现有隐藏代码。

执行真实 `TrendLinePrimitive.updateAllViews`，图表坐标接口使用轻量替身；每场景预热 1 次、采样 3 次，计时不含数据库读取、聚合、HTTP 或 Canvas 绘制。只读连接退出后才开始投影计时。单位 ms：

| 场景 | 绘图数 | 投影中位耗时 | 每次时区换算数 |
| --- | ---: | ---: | ---: |
| 最近 300 根窗口 | 19 | 0.5 | 0 |
| 完整 1,200 根历史窗口 | 19 | 1.8 | 0 |
| 隐藏后半段，仅传 780 根前缀 | 19 | 41.3 | 1,674 |
| 同一隐藏前缀，测试夹具排除带纯时间端点的线 | 16 | 0.2 | 0 |
| 同一隐藏前缀，无绘图 | 0 | 小于 0.1 | 0 |

“排除”仅是内存测试对照，没有删除或改写业务绘图。原始结果位于被 Git 忽略的 `tmp/trend-line-diagnosis/projection-baseline.json`。

这说明问题既取决于绘图数量，也取决于端点距当前投影窗口的距离、是否只有时间锚点。隐藏后 3 条线就足以把单次投影拉长到约 41 ms；反复触发会占用浏览器主线程。此结果确认了慢路径，不等于已取得生产浏览器完整性能记录。用户截图中另一环境的 16 条线、151–215 ms 是外部诊断记录，未作为本机实测值使用。

## 建议实施顺序

### 1. 统一绘图投影使用的时间轴

新增投影专用的时间轴元数据，来源为当前已经加载的完整 `bars`，只包含时间、桶结束时间及源序号范围。趋势线与斐波那契使用它定位；蜡烛、成交量、EMA、ABR 和选根交互继续遵循隐藏边界。

隐藏操作仅遮住价格，保留原时间槽，不能使右侧绘图重复从隐藏边界开始推算。这里不新增完整行情接口，不读取未揭示的未来行情，也不恢复隐藏 OHLC。

仅此一步不能覆盖真正落在已加载窗口之外的端点，所以应与下一步一起实施。

### 2. 消除窗口外逐根追赶，建立共享定位器

- 已加载时间轴先建立数值索引，按源序号/时间二分定位；保持聚合 K 线包含源序号、缺失行情与市场间隙的现有规则。
- 对纯时间且落在窗口外的端点，按交易日统计显示桶数量，处理首尾部分交易日；完整交易日使用累计计数。避免每次重绘从窗口边缘逐根推算到端点。
- 缓存端点在交易时间轴中的位置，按窗口边界换算逻辑坐标；同一个端点供趋势线、斐波那契和预览共享。
- 复用 `aggregation.ts` 的交易时段与桶边界规则。不能直接用“时间差 / 周期”替代 RTH/ETH 投影，必须保留周末、隔夜、夏令时、尾部不足一整周期的桶与跨周期锚定语义。
- 检查旧的循环达到上限后仍返回截断位置的行为；资源上限触发时不能把截断位置当成正确端点。窗口外源序号外推遇到休市缺口的准确性也需纳入回归。

这一步同时解决首次进入历史页和反复重绘的成本；只加一个重绘缓存会让首次计算、窗口更换后的卡顿继续存在。

### 3. 分离时间定位与屏幕坐标更新

平移、缩放、价格轴调整只更新屏幕 x/y，不重复计算交易日桶距离。样式、颜色或选中状态改变不使时间定位缓存失效；拖动一个端点只更新相关几何。

窗口增量追加、左侧补页、裁剪/替换、周期切换、RTH/ETH 切换、数据版本变化及会话切换，都要明确更新或失效。日历位置可继续复用，依赖实际已加载 K 线的索引必须按真实窗口更新，不能只按数组长度判断。缓存必须有容量上限。

统一合并同一帧内多次重绘请求，避免数据更新和绘图 effect 各自排队触发重复工作。正常推进仍逐源撮合并原子保存，绘图优化不改变交易状态。

### 4. 在上述修复后，再减少不可见线段工作

只对确认不与视口相交的有限线段跳过绘制和命中检测，保留所有绘图数据及对象列表。不能因为两个端点都在屏幕外就直接丢弃：线段仍可能穿过可见区域。选中端点、预览和价格标签需按既有规则处理。

这项作为第二阶段工作量优化，不用它代替第 1～3 项的投影修复；若会改变现有标签语义，应单独确认方案。

## 验证与验收

- 现有几何、趋势线、斐波那契及隐藏边界共 34 项单元测试已通过，作为当前行为基线；尚未实现修复或测量修复后收益。
- 新增回归：历史窗口内外的时间/源序号端点、两端都在屏幕外但穿过视口、隐藏/恢复、窗口前后补页与裁剪、1 分钟/5 分钟/2 小时切换、RTH/ETH、跨周末/DST、缺失源 K 线及尾部短桶。
- 验证绘图样式、拖动、端点吸附、命中优先级、价格标签、对象列表与历史本地绘图仍一致；全程不修改现有持仓、成交、进度或绘图保存内容。
- 使用本机同一组实际数据，分别比较首次投影、重复投影、下一根与窗口更换；再加入 16/50/200 条绘图、远距离时间端点和不同历史长度的隔离场景。
- 自动化断言重复视图更新不会再次逐桶进行时区换算；初次计算量应随交易日数及新锚点数增长，避免随“相隔 K 线根数 × 重绘次数”增长。
- 修复后再采集浏览器长任务与交互记录，覆盖普通推进和历史只读回放。目标是重复投影显著低于单帧预算；不能拿 primitive 微测替代页面整体流畅度验收。

本次只交付诊断与方案。实施预计涉及 `chart-drawings.ts`、`replay-chart.tsx`、两个绘图 primitive 及相关单元测试，无数据库结构迁移需求。
