# 行情时间聚合与查询

## 存储层级与显示周期

| 源周期 | 共用层 | ETH 层 | RTH 层 |
| --- | --- | --- | --- |
| 1s | 1min、5min、15min | 1H、4H | 1H |
| 1min | 5min、15min，1min 直接使用源表 | 1H、4H | 1H |

只为市场实际支持的时段构建对应层。其他源周期仅构建比源周期更大、且为源周期整数倍的上述层级，不复制源周期本身。

**存储层级不是显示周期白名单。** 保留现有秒／分钟／小时自定义入口，仍要求显示周期不小于源周期、是源周期的整数倍，并不超过 86400 秒。7s、61s、7min、45min、65min、90min、2H、3H、6H、8H、12H 等合法周期都走通用算法，不要求目标周期能被 15min、1H 或 4H 整除。

基础层按 UTC 时间网格对齐。ETH、RTH 的小时层按各自时段开盘对齐，分别存储；只有完整一小时／四小时时间跨度的桶才落入对应层。时间跨度完整不代表行情完整：保存实际源数量和理论数量，缺失源数据不补造。

项目现有 CME 股指 RTH 为芝加哥时间 08:30–15:15。预存六根完整 1H，最后 45 分钟由三根 15min 组成；RTH 日线通常读取九条摘要。ETH 的 17:00–次日 16:00 日线通常读取五根 4H 加三根 1H。收盘尾柱仍显示在所选周期中，不额外报“时长不足”；行情确实缺失才使用既有不完整状态。

1D 是对应时段的交易日日线，夏令时导致的 23／25 小时交易日仍是一根日线。全天连续交易沿用 UTC 日界。本次不添加节假日、午休、提前收盘日历，也不引入独立 EOD／期货结算价数据源。

## 源记录输出方式与质量判定（2026-10-20）

数据集记录 `barEmissionMode`：`TRADE_DRIVEN` 为按成交输出、`DENSE` 为连续时间网格、`UNKNOWN` 为来源规则未知。新 Databento CME OHLCV 导入自动保存按成交输出，适用于秒线与分钟线；普通 CSV 默认未知，也可在导入或“编辑行情设置”中明确选择。已有数据集默认未知，仅在确认来源后补标，不按文件名或记录密度猜测。

显示柱分别返回 `phase`（形成中／已收盘）和 `quality`（按源记录正常／未知／确认缺口）。收盘依据已揭示源时间是否越过目标桶末尾，不用当前系统时间，也不把文件结束直接视为交易桶收盘。按成交输出的柱允许少于理论时间槽数量；连续网格在已收盘后少槽才判缺口；未知模式少槽保留未知。明确传入的上游缺口证据仍会保留。`status` 为兼容现有消费者保留，`COMPLETE` 表示已收盘，并非验证了供应商全部成交的完整性。

图表仅对确认缺口绘制橙框；柱详情保留实际记录数／理论时间槽、时间状态与质量。未知覆盖的 PDF／AI 图像说明会标明未验证完整性。单凭 OHLCV 的空秒无法区分无成交与供应商漏报，正常状态仅表示按原记录合成，没有补造秒柱或修改价格、成交量及源序号。

新迁移 `20261020150000_bar_emission_mode` 只增加数据集元数据字段，不修改原行情或聚合表。改变输出方式不会使聚合代次失效，无需重导入或重建 OHLCV；显示缓存独立加入质量规则版本及输出方式，原始行情缓存保持原规则。追加已声明为按成交输出的数据时，不再把普通无成交间隔当作缺失确认；来源未知的追加仍保留时间间隔审核。

本机副本验证：49 张原有表的原有字段逐行一致，原始行情共 3,003,467 根，完整性和外键检查通过。该 ES 1s 数据集的同一 100 根 5min 窗口，在按成交模式下为 99 根已收盘正常、1 根形成中；连续网格模式会标出 82 根缺槽柱；未知模式将这 82 根记为完整性未知。三种模式的 OHLCV、源序号、源数量及聚合代次完全一致。

本次规则调整交付验证：123 个测试文件通过、1 个按原配置跳过，1,098 项通过、2 项跳过；类型检查、lint、生产构建及 40 个迁移的空库验证通过。本机原库备份后沿既有初始化路径升级，48 张业务表的原有数据逐行核对一致（排除数据集更新时间、新增元数据字段以及会持续更新的同步调度租约表）。已确认来源的 ES 1s 数据集标为按成交输出，活动聚合代次和回放进度保留，无需重新导入或重建聚合。浏览器完成 375px、1280px、1440px、1920px 检查，输出方式选项的键盘展开、Escape 关闭和焦点返回正常；长按柱详情可见已收盘状态、按源记录质量和 246／300 等实际记录信息，控制台无错误。

## 构建、代次与接口

空仓且无待处理订单的手动“下一根”可以直接复用时间聚合和索引边界，详见[空仓回放快速推进](flat-replay-advance.md)。有持仓或订单时仍沿源行情精确推进。

新表为 `MarketAggregationGeneration`、`MarketAggregatedBar`、`MarketAggregationJob`。数据集的 `activeAggregationId` 指向活动代次；代次记录规则版本、历史版本、时段指纹、源游标和未关闭桶状态。聚合主键为代次、时段范围、周期、桶开始时间。

- CSV／CSV.GZ 新导入在分块写入源数据时同步聚合。原始数据和该块聚合检查点在同一事务提交。聚合单独失败时保留已验证原始数据，数据集保持可用，面板允许单独重建。
- 追加和同步从活动代次的尾桶状态继续计算，先写暂存代次，再随原始尾部原子发布。原数据集尚未构建聚合时仍保持待构建，不能用新增尾部伪装整个历史已就绪。
- 面板“构建／重建聚合”扫描原始表，每批 4096 根，时间 O(N)、内存有界。新代次成功后原子切换，失败或取消保留原活动代次；检查点支持恢复。源历史、规则或目标长度改变后必须重新构建。
- 构建、追加、同步和元数据更正共用数据集租约。每个 worker 实例使用独立令牌，旧 worker 不能释放恢复后 worker 的租约。失联任务在租约到期后标为中断，等待用户恢复。
- 非活动成功代次保留至少 24 小时供在途读取使用，之后在后续任务中分批回收。原始行情、订单、成交和会话不参与清理。

`GET /api/market-datasets/:id/aggregation` 返回就绪状态、活动代次、规则版本及任务进度。`POST` 接受 `{ action: "rebuild" | "resume" | "cancel", jobId?: string }`；恢复需要任务 ID，重复构建请求复用活动任务。服务使用独立 Node worker，不要求浏览器持续打开。

数据集摘要和显示缓存携带聚合规则与代次标识；原始行情缓存仍按源数据历史版本管理。修改源周期或价格语义会使活动聚合失效。

## 通用读取与复杂度

1. 通过时间索引定位边缘真实源记录，按统一交易日历批量规划目标桶；数据空洞通过索引跳过，不逐源遍历整个历史。
2. 在各桶内依次选择完整包含于目标范围的最大摘要，剔除跨边界、跨时段或包含未揭示源序号的摘要。
3. 对未覆盖范围查询更细层，最后读取必要的源记录。每个 SQL 分支均有独立时间上下界及索引查找，分批 `UNION ALL`；不恢复旧的多区间 `OR` 扫描。
4. 各层保持有序，采用固定层数的线性归并，再计算 OHLCV 和形成状态。尾部源查询还受已揭示时间上界限制。

复杂度为 O(I log N + K + W)，N 为源数据总量，I 为索引查询区间数，K 为实际读取记录量，W 为规划／输出桶数。固定窗口读取不反复扫描全部 N 根源数据。自定义周期需要较多源记录时按既有预算缩小页面，通过游标继续读取，不禁用周期。

窗口、历史、指标预热、PDF 和 AI 使用同一读取服务。未完成新聚合构建的高于源周期请求返回 `409 / AGGREGATION_NOT_READY`；源周期读取仍可使用。没有某个显示周期的专用预计算层是正常情况，不属于未就绪。

窗口响应提供 `Server-Timing`、`X-Replay-Window-Strategy`、`X-Replay-Source-Rows`、`X-Replay-Summary-Rows`；设置 `REPLAY_QUERY_METRICS=1` 可记录查询数。模拟撮合仍逐源推进，显示层不参与撮合和权益计算。

## 升级与本机验证

按[升级指南](upgrade.md)选择 Prisma 迁移或旧初始化路径。新增迁移 `20261020120000_time_aggregation` 删除两张旧块表和旧游标，创建新表及指针；不搬迁原始行情、不转换旧摘要、不自动回填。升级后在面板逐个构建已有数据集。回退旧代码需要兼容的升级前备份，不能直接连接新结构。

2026-10-20 在本机一致性副本完成验证：46 张原有业务表逐行摘要相同，原始行情 1,783,470 根，`integrity_check=ok`、外键检查为空；完整 39 个 Prisma 迁移也在隔离空库通过。生产环境和其他平台需按目标机器验收。

本机 1min MGC 数据集含 1,746,688 根源数据，返回相同的 500 根柱。旧算法读取和聚合的复现结果，与新完整窗口 API 的 OHLCV、序号及状态逐字段一致。native / DELETE 的首轮重复请求中位数如下（后端进程内测量，不包含浏览器和网络）：

| 周期 | 旧窗口算法中位数／P95 | 新完整 API 中位数／P95 | 新读取源行／摘要行 |
| --- | --- | --- | --- |
| 6H | 12,708／13,411 ms | 54／56 ms | 0／1,448 |
| 8H | 13,986／14,328 ms | 43／60 ms | 0／967 |
| 1D | 17,244／21,868 ms | 90／114 ms | 0／2,568 |

每组取首次请求及五次重复请求，首次与重复值分别保留；没有清理操作系统文件缓存，不能将首次请求称为磁盘冷读。重建约 175 万根 1min 用时约 77 秒；额外 100 万根合成 1s 行情重建约 32 秒。耗时受机器和磁盘影响，不构成生产承诺。

同机 `better-sqlite3 / WAL / FULL` 也完成了 ETH／RTH 和 1s／1min 测试；其中 MGC ETH 500 根的 6H、8H、1D 中位数约为 142、110、135 ms，P95 约为 161、125、166 ms，读取行数与上表相同。驱动和诊断配置不同会影响接口耗时，不应套用 native 的具体毫秒数。

`EXPLAIN QUERY PLAN` 验证源查询各分支为 `SEARCH MarketBar USING INDEX MarketBar_datasetId_timestamp_key (datasetId=? AND timestamp>? AND timestamp<?)`；摘要为聚合主键索引的 `generationId + scope + intervalSeconds + bucketStart` 范围查找。源区间在最终读取前合并相邻部分；摘要选择仍保留目标桶边界。扩大未来历史的回归用例同时核对返回结果及实际源行／摘要行数保持一致。

两份原有数据集完成构建后，原始表含索引约 292.70 MiB，新聚合含索引约 87.84 MiB，比例约 30.01%；旧块约 6.07 MiB／2.07%。重建期间还需容纳新旧代次，SQLite 删除记录释放页供复用，不会自动缩小数据库文件。
