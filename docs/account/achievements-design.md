## 2. 产品定位与范围

成就记录交易经历、训练积累和账户成果，与境界 / 经验系统并行。沿用现有无登录练习档案，不增加真实用户认证、角色、排行榜或多租户隔离。

首版范围（已确认产品选择见第 19 节，其余交互细化为实施设计）：

- 成就自动解锁，不需要领取；只奖励徽章和展示记录，不额外发经验或练习资金。
- 个人档案展示摘要，独立成就页查看全部；普通导航不增加一级“成就”栏目。
- 用户明确提出的连续止损 / 止盈、考核与出金方向都纳入首版目标；可分阶段开发，不能把仅完成累计类视为整个首版完成。
- 首次历史任务在维护页预检查后明确启动，系统随后自动计算和授勋；证据不足明确说明统计范围，不让用户手动勾选代替事实。已启动任务可自动恢复，日常新增成果自动处理。
- 已解锁结果独立持久化，来源删除、会话归档或后续失败不会自动撤销。
- /admin 维护页不出现在首页和业务导航，专用于预检查、补算进度、校验和重试。
- 交易、撮合、关卡、复盘、账户晋级及出金继续使用原规则，成就只消费已保存的结果。

不纳入首版：签到、在线时长、观看图表、单纯推进 K 线、会话报告奖励、AI 质量评分、全平台稀有率、强制社交、人工直接授勋、清零成就、账户重置和数据清理。

## 3. 成就目录

### 3.1 首版目录

稳定 key 用于程序和唯一性。下表十个系列的中文名和阈值已由用户确认，必须集中定义；后续产品变更另行记录，不通过改名改变稳定身份。

| 稳定 key | 名称 | 逐级阈值 | 计数与证据 | 开发阶段 |
| --- | --- | --- | --- | --- | --- |
| first-cycle | 初试锋芒 | 1 | 首个完成的持仓周期 | A |
| completed-cycles | 百炼成钢 | 100 / 500 / 1000 | 已结算完整持仓周期累计 | A |
| first-review | 落笔为证 | 1 | 首次有效逐笔复盘 | A |
| completed-reviews | 复盘成册 | 10 / 50 / 100 | 首次有效逐笔复盘累计 | A |
| passed-evaluations | 过关斩将 | 1 / 5 / 10 / 20 | 考核通过累计，每会话 + 轮次一次 | A |
| successful-payouts | 兑现时刻 | 1 / 5 / 10 / 20 | 成功出金流水累计 | A |
| payouts-in-round | 长青账户 | 3 / 5 | 单个会话内同一账户轮次的成功出金次数 | A |
| foundation | 破境之证 | 1 | 原系统实际筑基突破记录 | A |
| stop-loss-streak | 逆风而行 | 5 / 10 | 同一会话 / 轮次的连续纯止损完成周期 | B |
| take-profit-streak | 乘风而上 | 5 / 10 | 同一会话 / 轮次的连续纯止盈完成周期 | B |

已确认的首版共 10 个系列、23 个可解锁阶段。页面分母从实际启用目录计算，不把尚未上线的系列算作用户未完成。

名称“逆风而行”是经历记录，不评价策略优劣。止损类提示使用中性语气，不播放亏损庆祝，不使用羞辱性称号。

### 3.2 后续候选

| 稳定 key | 名称 | 建议阈值 | 需补充的可靠记录 |
| --- | --- | --- | --- |
| reviewed-losses | 败中求解 | 10 / 30 / 50 | 完成周期净亏损与其全部逐笔日志有效复盘的映射 |
| review-completion-streak | 有始有终 | 连续 10 / 20 周期 | 周期完成顺序、全部应复盘日志身份及各自首次完成事实 |
| completed-gates | 关卡历练 | 1 / 5 / 10 轮 | 每次关卡真实完成事件和稳定轮次身份 |
| recovery-evaluation | 重整旗鼓 | 1 | 同会话前一轮失败、重新考核关系与新轮通过事实 |

用户已确认以上四个候选留待后续，不纳入首版；其名称和门槛仍是后续建议。候选不默认启用，不显示为首版灰色锁。特别是当前关卡 activationCount 记录开启次数，不能直接当成完成次数。

### 3.3 分级与版本

- 每个系列一张主卡，默认展示最高已获阶段和下一目标。
- 各阶段分别保存一次性解锁记录，详情可展开全部等级、日期和来源。
- 解锁唯一键为“用户 + 成就 key + 阶段 key”，不能包含规则版本而使同一徽章重复发放。
- 阶段 key 独立稳定，例如 tier-1，而不是把会变动的中文名当身份。
- 规则版本用于解释当时条件和重建过程，解锁时保存阈值及条件快照。
- 修改未来阈值不得静默重写旧解锁条件或撤销旧徽章。实质不同的成就使用新 key；同一系列规则调整须单独明确旧获奖者与未解锁者的适用范围。

### 3.4 新增成就与新增指标的区别

数据库不能按每个徽章添加布尔值或计数字段。规则目录引用可复用的 metricKey（例如 completed-cycles），一个指标供首笔交易、百炼成钢及未来更高阈值共同使用。

至少区分三类版本：展示修订、成就/阶段目录修订、指标计算指纹（metricKey + evaluatorVersion + 证据要求）。不能用一个全局 hash 的变化决定全部重算。

| 变更 | 字段 / 迁移 | 处理方式 |
| --- | --- | --- |
| 修改名称、说明、图标、排序 | 无 | 更新目录和文案，不重算进度 |
| 用已有完整指标新增徽章或更高阶段 | 无 | 从该指标已发布进度判定，仅补唯一解锁；不重新物化历史 |
| 已发布阶段改变实质门槛 | 通常无 | 保留原阶段及其快照，发布新阶段或新 key；旧获奖不撤回 |
| 新增组合条件，现有事实已包含所需信息 | 通常无 | 新增纯 evaluator，只重建受影响指标 |
| 新增原来没有记录的行为 | 可能扩展通用证据 | 先接通新事实/证据版本；未知旧值不能补成 true 或 0 |
| 新增高频查询维度、索引、唯一性或核心类型 | 按需迁移 | 证明现有通用结构不足后，按当前升级指南执行增量 |

“完整指标”必须具备匹配的计算指纹、水位和覆盖范围；发现缺口则补该指标的证据，不能只看 UI 上有一个数字。已有可靠总量达到新阶段时，可以直接解锁；无法定位原达成日期就标记历史达成，不为一个日期重扫所有历史。

目录禁用某系列时保留已获记录，单列“已归档成就”；启用目录分母不把归档徽章混入，避免已获数量大于当前总数。首版不开放维护页直接编辑阈值或运行任意规则代码。

## 4. 资格、归属和计数单位

### 4.1 个人资格

建议与现有成长资格一致，完整定义继续归[用户成长当前规则](user-growth-design.md)维护：

- 成果必须属于明确的用户及具有成长资格的训练会话。
- 未归属、全部用户视图、实盘重演不产生个人成就。
- “全部用户”不是一个获得成就的虚拟用户。
- 根据业务会话真实归属结算，不读取浏览器当前选择来决定获奖者。
- 归档不取消既有资格；归档训练会话后补写有效逐笔复盘仍可产生对应成就事实。
- 旧的未归属会话不补归属，不补经验；本方案承接已有合格成果，不改变此前的资格政策。

### 4.2 稳定业务身份

| 成果 | 业务单位和去重身份 |
| --- | --- |
| 完成交易 | 原系统完整持仓周期；会话 + 轮次 + 逻辑周期 ID |
| 有效逐笔复盘 | 原逐笔日志稳定身份；同笔首次完成一次 |
| 考核通过 | 会话 + 账户轮次；手动与自动入口共用同一成果 |
| 成功出金 | 唯一成功出金流水，不同时将对应账户事件再算一次 |
| 筑基突破 | 原系统突破记录 |
| 关卡完成（后续） | 稳定关卡实例身份；不能仅用源序号或当前 activationCount |

复用 [logicalId](../../lib/replay-sessions/identity.ts)、[会话作用域](../../lib/replay-sessions/scope.ts)和现有映射；projection ID、显示编号、图表周期、页面排序都不能成为唯一成果身份。来源键使用明确的结构编码，不直接拼接可能含分隔符的任意名称。

### 4.3 连续止损和止盈的首版口径

- 单位为完整持仓周期，按照现有周期定义计数，部分平仓不单独增加一笔。
- 消费原系统已经产生的平仓事实，不为了成就重跑撮合或复制原成交算法。
- 一个周期中所有实际减仓 / 平仓部分均来自保护止损成交，归为纯止损；全部来自保护止盈成交，归为纯止盈。
- 有多个退出原因、手动平仓、反手关闭旧周期、账户失败强平，分别归为 MIXED / MANUAL / REVERSE / FORCED；这些结果中断两个纯退出连续数。
- 移动止损可能盈利，止盈成交扣费后也可能没有净利润。分类按实际退出原因，不按盈亏正负推断。
- 加仓、挂单、撤单和未结束周期不增加或打断连续完成周期数；它们本身不是新完成周期。
- 非匹配的已完成周期将该连续数归零；已解锁等级和历史最佳保留。
- 连续范围固定为同一用户、同一回放会话、同一账户轮次。默认账户以该会话的固定默认轮次表示，不能把所有默认账户合并成一条序列。
- 新轮、新会话开启新的连续范围；不同范围不能拼接。回放显示周期、时区和 ETH / RTH 切换不改变顺序。
- 同一源 K 线可能完成多个周期，必须有真实执行先后。新事件捕获稳定业务顺序；不能用回放时间、随机 ID 字典序或界面行号猜测。
- 旧记录无法还原执行顺序或退出原因时标记 UNKNOWN，断开可证明的连续区间，不当作正常止损、止盈或盈利。
- 历史有效尾段可与上线后事件续接，前提是能证明中间没有漏项；否则新建连续区间，并向用户说明覆盖范围。

建议详情文案：“按同一会话、同一账户轮次中完整结束的周期统计；分批止盈后又止损属于混合退出。”

## 5. 用户界面与反馈

### 5.1 入口

- 用户档案身份与经验区域下方增加紧凑成就摘要，显示已解锁阶段数、最近解锁、最多三枚展示徽章及“查看全部”。
- 独立页面建议为 /users/{userId}/achievements；标题明确正在查看的用户。
- 头像菜单提供“成就”入口；回放中按会话实际归属打开，遵守现有“不在回放里切换归属”的边界。
- 当前为全部用户或未归属时，提示选择具体用户查看，不生成全局混合进度。
- 不在全局顶栏增加高权重一级导航，不在图表上常驻整面成就墙。

### 5.2 成就页

采用现有标准内容页结构：

1. 面包屑、用户名称和“成就收藏”标题。
2. 已解锁阶段数 / 启用阶段总数；明确统计的是阶段，不与系列数混用。
3. 状态筛选：全部、已解锁、进行中、未解锁；分类筛选：交易、复盘、自营、成长。
4. 每个系列一张卡：徽章、名称、条件、最高阶段、下一目标进度和详情入口。
5. 详情显示规则版本、各阶段日期、历史补算标记、必要来源摘要和可用来源链接。

连续类显示“当前”和“历史最佳”，不能把历史最佳冒充当前连续。多个会话分别有当前数时，概览显示“最高进行中记录”，详情说明所属范围；用户从某个回放进入时可突出该会话。

显示状态：

| 状态 | 文案及行为 |
| --- | --- |
| 尚未开始 | 0 / 目标；保留清晰条件 |
| 已有进度 | 显示实际数值，进度填充最多 100% |
| 已解锁 | 勾选、等级及解锁时间；不依赖单一颜色 |
| 同步中 | “正在整理历史成就”，保留已知数据 |
| 历史证据不足 | “历史记录不足，此项自启用后统计”或明确已覆盖范围 |
| 查询失败 | 保留已知结果，提示重试，不显示成就归零 |
| 来源已删除 | 保留成就和摘要，去掉无效跳转 |

进度、总数、来源列表由服务端分页 / 限量读取。不得向浏览器一次返回全部交易或补算原始证据。

### 5.3 展示徽章

用户已确认最多展示三枚，属于用户档案展示偏好。仅可选择本用户已解锁的系列，按槽位保存，同系列不重复。系列升级时展示其最高已获阶段，详情保留所有等级。首次没有选择时不伪造“获得”或强制自动收藏。

### 5.4 解锁提示

- 原业务成功后先保证结果保存，成就后台处理完成后才提示真实解锁。
- 使用轻量状态提示，可进入详情；不暂停回放，不夺焦点，不覆盖下单或播放控制。
- 同批多项合并为“解锁 3 项成就”；连续止损类使用中性通知，不使用盈利色或庆祝音效。
- 历史补算只提示一次汇总，不逐项重播动画；刷新不重播已有解锁。
- 通知明确归属用户，不能因浏览器选择变化把别人解锁显示成当前人的奖励。
- 复用现有反馈机制与持久化回执；首版不扩展跨设备已读系统，失败时可在成就页查看。

### 5.5 视觉规范

遵循[唯一 UI 规范](../ui/ui-guidelines.md)和现有明暗主题。徽章可有统一的类别图形与等级标记，文字条件始终可读；未解锁降低强调但不降低到无法阅读。没有新增全局颜色或动效例外，不画大型发光徽章、满屏彩带和虚构稀有率。所有固定文案通过 copy；数值经 lib/format.ts。完成键盘、焦点、ARIA、对比度和减少动画检查。

## 7. 模块职责与事件链路

建议新增 lib/achievements/，不把规则堆进 React、API 或撮合引擎。

| 建议模块 | 职责 |
| --- | --- |
| catalog.ts / rules.ts | 成就/阶段目录、可复用 metricKey、独立计算指纹和纯规则 |
| evidence.ts | 权威事实适配、通用退出证据、来源和归属验证 |
| settlement.ts | 在既有事务中幂等追加最小消费索引/补充证据，不计算全历史 |
| read.ts | 已发布进度、摘要、详情和来源分页 |
| jobs.ts / runtime.ts | 共享执行槽、租约、恢复、短批调度 |
| backfill.ts | 固定范围、历史适配、指标重建、追平和按项发布 |
| maintenance.ts | 预检查、计划验证、启动和重试 |
| validations.ts | 参数、证据版本、payload 和批次上限 |

正常链路：

~~~text
原业务成功事务
  ├─ 原成长事实和业务记录照常保存
  └─ 成就最小索引 / 必要补充证据，同源最多一份
          ↓ 提交成功后合并唤醒；唤醒丢失由低频发现兜底
共享有界执行者优先消费新增事实
          ↓
只更新受影响指标 → 判定引用它的阶段 → 解锁/进度/游标同事务
          ↓
页面读取持久化结果
~~~

UserGrowthFact 继续是累计成果的权威证据。AchievementFact 只承担稳定消费序号、来源引用及原数据缺少的补充内容，不复制完整成长流水或每个成就的独立事件。写入数量按实际来源事件增长，不按“事件 × 成就 × 等级 × 版本”增长。

### 7.1 必须覆盖的源触发矩阵

| 成果 | 接入点 | 捕获条件和去重 |
| --- | --- | --- |
| 周期关闭（含反手关闭旧周期） | persistTrades / 原 transition 链路及 settleClosedCycle | 真实 CLOSED；更新整个周期退出证据，按稳定逻辑周期一次 |
| 首次有效逐笔复盘 | 原保存事务中的 settleGrowth(REVIEW) | 原有效性/采用来源校验通过；同笔首次，原业务失败不捕获 |
| 考核通过 | 自营自动晋级与手动晋级的两个 settleGrowth(EVALUATION) 路径 | 会话 + 轮次一次，不将账户事件再计一次 |
| 每次成功出金 | 原成功提款事务的 settleGrowth(PAYOUT) | 每条成功流水一次，经验为 0 的后续出金仍捕获 |
| 筑基突破 | breakthroughFoundation 直接创建 BREAKTHROUGH 事实的事务 | 该路径不经过 settleGrowth，必须明确接入 |
| 候选关卡完成 | 原关卡从 active 变为完成的保存事务 | 后续启用时增加实例完成事实，不能消费“开启”代替完成 |

新事实只能在业务归属和资格校验后捕获。不能只给 settleGrowth 一个通用钩子就宣称触发已完整覆盖。

### 7.2 事务与唤醒

- 原业务失败或回滚不留事实。事实捕获失败遵循原事务失败语义，不能业务成功后悄悄吞掉必要证据。
- 捕获为有界本地写入；不在事务中做重算、读全历史、等待队列、网络调用或开启后台进程。
- 不再次调用发经验、扣费、提款、晋级；批量推进沿用其原子保存，不为成就拆散原批次。
- 只在事务提交确认后合并唤醒执行者，不能在事务回调里启动消费。唤醒是提示，持久事实才是可靠来源。
- 现有请求幂等、源序号、投影版本和会话可写校验继续保留。
- UUID 使用统一 createUuid；纯服务端可用 node:crypto。普通 HTTP / 局域网不依赖浏览器 randomUUID。

## 8. 建议数据模型

以下是逻辑模型，不是现有 Prisma schema。允许合并职责兼容的表，禁止为每个徽章新增列；表数量不是 2G 内存占用的直接决定因素，实际行数、查询范围、payload 和常驻进程才需约束。

| 模型 | 最少职责与主要字段 | 唯一性 / 索引建议 |
| --- | --- | --- |
| 代码内目录 | achievementKey、tierKey、metricKey、evaluatorVersion、证据要求、enabled、展示修订 | 一份指标可服务多个系列/等级 |
| AchievementFact | 明确递增 seq、userId、sourceKey、type、growthFactId/其他来源引用、scopeKey、必要业务顺序、事实时间、补充 payload String、evidenceVersion | sourceKey 唯一；(userId,seq)、(userId,type,seq)、(userId,scopeKey,businessOrdinal) 按实际查询配置 |
| UserAchievement | userId、achievementKey、tierKey、规则/条件快照、日期可信度、recordedAt、来源摘要 | (userId,achievementKey,tierKey) 唯一；不将 ruleVersion 放进唯一键 |
| UserAchievementState | userId、metricKey、activeGeneration、activeFingerprint、version、lastAppliedSeq、bootstrap/覆盖状态 | (userId,metricKey) 唯一；明确的发布指针和 CAS 落点 |
| UserAchievementProgress | userId、metricKey、generation、scopeKey、current/best、覆盖、状态快照 | (userId,metricKey,generation,scopeKey) 唯一；只读 State 指向的代际 |
| UserAchievementShowcase | userId、slot、achievementKey | (userId,slot) 唯一，同系列不重复，slot 1～3 |
| AchievementSyncState | 启用时间、目录计划、水位；固定全局运行槽的 ownerToken、leaseUntil、运行任务身份 | 全局槽用稳定唯一键，不只是每个 Job 自己的锁 |
| AchievementJob | mode、归一化范围、目录/指标指纹、边界、状态、租约、重试、摘要 | 同一计划幂等；(status,retryAt)；范围重叠校验 |
| AchievementJobItem | jobId、userId、metricKey、generation、阶段、持久游标、水位、覆盖、错误 | (jobId,userId,metricKey) 唯一；按指标而非每个徽章/等级创建 |

### 8.1 通用结构与数据量约束

- 累计类优先引用已有独立 UserGrowthFact；AchievementFact 不重复存 xpDelta、完整 sourceSummary、复盘正文等可由权威事实解释的内容。
- 一个 sourceKey 一份消费索引，历史导入与实时捕获共用身份。新增成就/版本不复制事实。
- JSON String 按 evidenceVersion / evaluatorVersion 使用 Zod 校验；不能无版本地往一个自由 JSON 塞任意字段。缺失旧字段按 UNKNOWN 解释。
- 新增事实 payload 目标不超过 2 KiB、硬上限 4 KiB；必要身份不截断，通过明确结构限制实现。事实不含行情、完整交易历史或密钥。
- 进度按指标共享；同一指标的 1、100、1000 阈值不各维护一套累计数。scope 只用于确实按会话/轮次计算的指标。
- 正常最多保留一个 active 和一个 staging 进度代。失败代保留以便恢复，存在失败代时不再无限创建新代；旧代退休须有明确保留政策，不删除独立解锁、原成长事实和待复核失败现场。
- 用户发现、计划项和错误详情分页保存，不把全部用户/全部来源键嵌入一个 Job JSON。单项快照上限 8 KiB，单任务错误样本上限 100 条，单条摘要上限 2 KiB，其他错误按原因计数并保留定位依据；不记录复盘正文。
- 原会话/轮次来源只保存稳定引用和必要摘要，不把独立获奖或成长证据挂在可删除来源的 Cascade 关系上。
- Fact.seq 是消费顺序。只有在原交易事务真实闭合顺序内生成的新实时序号才能证明该范围的新事件顺序；历史补导序号不能替代历史执行顺序。
- 历史围栏不能只依赖 cuid 排序或未受保护的长期 rowid。使用稳定来源身份；遇来源生成/维护边界变化使游标失效时停止核对，不继续猜。
- 关键查询用范围索引和 EXPLAIN QUERY PLAN 验证；避免从 JSON 提取字段全表筛选。新增索引按真实查询证明需要，避免无用索引增加每次源写入成本。

### 8.2 连续类所需的一次性通用字段

“所有退出原因一致”必须跨部分减仓、批量推进和重启持续记录，不能只读取最后一笔 fill。建议在现有 PaperTrade 增加通用可空字段 exitReasonMask、exitEvidenceVersion（最终字段名在实现中确定），属于首版的一次性证据能力，不是每新增成就增加字段。

- 新周期创建时以当前证据版本、空位集开始。
- 消费原 transition，每次实际减仓/关闭将真实退出原因合入位集；直接合并进原 PaperTrade 更新，尽量不增加一次独立数据库往返。
- MANUAL / REVERSE / FORCED / UNKNOWN 等也进入位集；强平来源复用现有账户失败证据，不能按净亏损猜。
- 完整结束时从位集生成最终分类，并将精简分类及可信顺序放入独立成就事实；周期被删后事实仍保留。
- 旧周期字段默认为 null，含义是未知，不是“从来没有减仓”。旧未平完周期仅在历史映射完整可证时补齐，否则保留 UNKNOWN 位，避免下一笔止损把混合周期判成纯止损。
- 不在每次平仓时查账户所有 fills，不以 FIFO cycleKey 未核验地代替完整 PaperTrade 身份。
- 此字段方案需要按升级指南走增量迁移；以后相同证据上的新阈值不再迁移。开发如选择等价的独立累积证据表，需保持同样事务和旧 null 语义，并说明额外写入成本。

### 8.3 发布指针

- UserAchievementState 是每个用户/指标的唯一活跃指针，不靠“取最大 generation”猜当前版本。
- 正常增量提交须匹配 activeGeneration、activeFingerprint、version，并以 CAS 前进 version / lastAppliedSeq；失配则丢弃本次计算并重新读取。
- 重建只写该指标的 staging，旧已发布值可读。追平完成后带 job owner、旧指针和期望 version 做短事务切换。
- 按用户/指标项发布，不用一个包含所有用户、所有 scope 的大事务。Job 汇总所有项状态，可以有部分完成并如实显示。
- 同一指标的增量与 staging 发布不能并行争写：进入切换前冻结其应用权（源事实仍追加），追平后切指针，后续事实从新游标继续。
- 用户指标状态、JobItem 游标、解锁和指针的相关更新必须原子提交，不能先记完成再保存结果。

## 9. 增量计算、去重与重建

### 9.1 正常增量

- 后台按事实类型查受影响规则，不每次遍历全部用户、全部成就和全部交易。
- 先校验事实唯一性、活跃指标指针和处理位置，再进行一次指标计算；该指标引用的多个徽章只判定阈值，不重复累加。
- 进度、解锁、已处理位置及 UserAchievementState 的期望版本在一个短事务提交。崩溃不能出现游标已前进而成就尚未写入。
- 当前运行轮次租约有效才可提交；失去 ownerToken / 租约的旧 worker 必须停止，不能晚到覆盖。
- UserAchievement 唯一约束是最终兜底，不是靠前端按钮禁用或内存布尔值实现去重。

### 9.2 顺序型规则

历史事实可能晚于新事实导入。连续成就必须按真实业务顺序计算：

- 每个会话/轮次独立维护流位置；新周期捕获可靠递增 ordinal，或采用能证明相同执行顺序的既有命令序号。
- 业务写入通过已有 transition 消费顺序捕获证据，不修改原撮合规则。
- 首次补算未完成时，新事实先持久化，相关顺序型规则等待历史边界对齐；不影响原交易提交。
- 对完整历史片段、UNKNOWN 间隔和上线后片段分别归并，只在连续性有证据时续接。
- 不能先算新事件，再把旧事件按入库顺序接到末尾，也不能把两个片段的最佳值相加。

### 9.3 手动重新校验

重新校验不向旧进度再加一遍历史。以受影响 metric 为单位建立唯一 staging generation，按第 8.3 节追平并 CAS 发布。重建中继续显示旧指针的已发布进度并标记更新中，不能直接对新旧快照做 max 或覆盖。

已获徽章独立保留。新代际发现历史缺失或规则差异时，记录解释，不自动扣回徽章。需要撤销错误授予的政策不属于首版。

## 10. 历史补算设计

### 10.1 来源优先级和覆盖

| 项目 | 优先来源 | 历史边界 |
| --- | --- | --- |
| 累计周期、复盘、考核、出金 | UserGrowthFact 已结算增量；必要时与 UserGrowth 投影核对 | 原会话已删仍可承接 |
| 同轮出金 | 有会话/轮次身份的独立成功出金事实 | 不要求来源会话仍存在；身份缺失则不能猜 |
| 筑基 | UserRealmRecord / 原突破事实 | 不仅看当前经验满足条件 |
| 连续止损/止盈 | 合格周期对应的完整退出事实及可证明执行顺序 | 缺少原明细时无法仅凭 CYCLE 次数恢复 |
| 复盘闭环/关卡等候选 | 专用完成与映射事实 | 未记录过的行为不从当前状态反推 |

不能用“当前复盘文本非空”推断过去首次有效复盘，不能用净亏损推断保护止损，不能用当前出金阶段推断曾经的考核次数。

已删除历史能支持累计类而不能支持连续类，是正常覆盖差异。对完整且可证明的片段可补发已达门槛；不能跨缺失片段拼接。未知既不算失败，也不能当作成功，它只结束可证明连续区间。

### 10.2 一次补算的阶段

~~~text
DISCOVER → MATERIALIZE → EVALUATE → CATCH_UP → PUBLISH → SUCCEEDED
                              └─ 个别记录证据不足 → 记录覆盖限制
任一阶段暂时失败 → 保留游标并重试
持续或结构性失败 → FAILED，维护页处理
~~~

1. DISCOVER：固定规则指纹、用户范围和各来源截止水位 H。用户清单分页固化，新建用户由正常增量接管，不在运行中漂移分母。
2. MATERIALIZE：按稳定游标读取 H 内已有合格事实，转换为专用事实并按 sourceKey 幂等写入；与实时捕获重叠的同一来源只保留一份。
3. EVALUATE：在新代际计算累计及已验证的顺序型进度，不直接覆盖线上旧进度。完整保留原规则增量与缺失范围。
4. CATCH_UP：消费补算期间新增事实。新增捕获已上线，不丢事件，也不让已导入历史重复计数。
5. PUBLISH：按用户/指标项，在短事务内校验全局槽、Job 租约、指标指纹、activeGeneration 和 version，完成最后有界追平，CAS 发布指针及唯一解锁；不把全站发布合成一个事务。
6. SUCCEEDED：保存最终水位、用户/规则覆盖和统计。数据不足记录为已完成但有覆盖限制，不进行无限失败重试。

捕获的 H 不能用回放行情日期或本机当前时间代替一致快照。允许各权威源使用独立围栏，但必须证明统一去重及边界对应。

追平时事实仍在增长：如果最后差额超过单批上限，继续后台追平；小差额才在最终短事务处理。发布后，后续事实由同一代际增量游标继续消费。不能“读最大值、先标完成、随后再异步保存”制造窗口。

### 10.3 删除、断电和部分错误

- 任务每批同时提交事实/进度与游标。关页不影响服务端执行，断电后从最后一次成功位置继续。
- 已删除来源以独立成长事实承接累计；专用明细尚未捕获就已删除时标记证据不足，不能伪造细节。
- 遇到来源损坏、归属冲突或未识别版本时隔离该条 / 项目并保留错误；其他可独立验证用户可继续。
- 批次明确回滚后才允许重新执行；提交结果不确定按下述流程处理，不能笼统归为暂时失败重放。
- 数据读取故障是 ERROR，不显示成就 0 或冒充“历史不足”。
- 同步不重发经验、不操作钱包、不触发晋级、不修改历史交易或模拟重新下单。

#### 提交结果不确定的处理

复用 [SQLite 写入封装](../../lib/sqlite-write.ts)的语义。SqliteCommitUncertainError 表示事务回调已返回而 COMMIT 未得到确认，不等于已回滚。

1. 停止本批及其副作用，不能重放事务回调、重新通知或重新累加。
2. 重新建立读取，按唯一来源键、持久游标、JobItem 状态、发布指针/version 和租约核实实际提交结果。
3. 证明整批已提交则承接已保存游标；证明未提交且新执行者有有效资格才重试。
4. 无法确定则将该项标为需核对的失败，保留证据，不能用自动重算掩盖结果不确定。

批次使用稳定 batch 标识或同等原子回执以便核实。默认 backgroundWritePolicy 可等待约 30 秒，成就不得直接照搬；采用第 11.4 节的专用短预算及 owner-qualified 写入。

### 10.4 达成时间

至少区分：

- attainedAt：能证明达到门槛的现实系统结算时间，可为空。
- recordedAt：成就系统实际写入时间。
- replayOccurredAt：相关回放行情时间，仅来源详情展示。

能够逐条重放历史事实时，采用达到门槛的那条事实的系统结算时间。只有可靠总量而无法定位原达成时刻时，显示“历史达成，本次同步”，不拿补算时间伪装原达成时间。

### 10.5 预检查

预检查使用与正式补算相同的资格和纯规则，固定范围与水位，显示：

- 可处理用户数、已具备成就、预计新增阶段、预计更新进度；
- 证据不足的用户/规则数量和原因；
- 当前规则版本、检查时间及任务边界。

预检查不写解锁、正式进度或业务原数据；允许持久化维护任务、计划和错误摘要。预览“无成就数据写入”不等于整个系统没有任务元数据写入。

正式启动引用服务端计划 ID。只补算已审阅的规则和 H 内数据；后续事实由增量接管。规则已变、范围冲突或依赖证据失效时返回计划过期，要求重新检查，不能按陈旧预览扩大操作范围。

## 11. 启动时机、调度和性能

### 11.1 2C2G 下的启动策略

用户已确认首次历史补算由维护页预检查后明确启动；服务启动只注册轻量调度、恢复已经启动的任务和消费日常新增事实。这样避免服务器重启时同时进行 Next 预热、行情任务和首次全历史扫描。

- 数据库实际结构通过当前启动检查后注册，不在 register() 中 await 全量任务。
- 从未启动的 bootstrap 标记为待初始化，重启不能把它偷偷变成全量执行。
- 已启动但中断的任务按原计划/游标恢复，并遵守低资源暂停条件；已经完成的同版任务直接跳过。
- 构建、静态生成、隔离预览和测试不启动真实处理，沿用现有环境隔离。
- 新建普通用户只初始化本用户状态并处理以后事实，不触发全站历史任务。
- GET、刷新、头像打开、用户切换及进入维护页不隐式创建补算。
- 首版不在服务首次启动时自动发起历史全量扫描。未来若另行确认首次自动补算，只改变建任务的触发，不另建扫描算法，仍受资源门控与唯一计划约束。

### 11.2 成就更新和指标计算分开调度

执行第 3.4 节变更矩阵。展示修订、阶段目录修订与指标计算指纹分别维护。

- 新徽章 / 阶段使用已有完整指标时，只分页读取相关用户的已发布进度，执行便宜的阈值检查并幂等补解锁，不走 MATERIALIZE 全链路。
- 完整覆盖不足、新的计算谓词、证据版本变化时，维护页显示受影响指标并预检查后重建；不连带重建无关指标。
- 新行为先捕获证据，缺失历史按 UNKNOWN；不能用默认字段值补造达成事实。
- 代码不支持某历史 evaluator 版本时停止对应任务，不能在同一个旧计划里换成新算法继续。
- 对中文名/图标改变不排计算任务。已获徽章和原阈值快照不因更新而撤销或重新发一份。
- 在途范围按“用户集合 + metricKey + 计算版本”归一化；全部用户与某个用户范围相交时也检测冲突，不能仅比较 scopeHash 相等。

### 11.3 全局运行槽、租约和公平调度

- 进程内单例只能防热更新重复定时器。全局运行槽持久化在 AchievementSyncState；领取 Job 与获取/续租该槽在同一短事务原子完成。
- 所有预检查、历史补算、重新校验和失败恢复共享单槽，多进程不同 Job 也只能有一个成就执行者。每个 Job 自己的租约不能代替全局槽。
- 同一执行者内优先处理小批新增成果，剩余预算才处理历史。正在 bootstrap 的用户/指标先可靠落事实，相关顺序应用等待边界对齐，不使其他用户的新增成果长期饥饿。
- 正常增量不逐事件创建 Job，仅核验全局 slot ownerToken、有效租约和指标发布指针/version；计划任务另核验 Job/JobItem 的 ownerToken、generation 和状态。任一适用条件失配即回滚停止。
- 只在有任务的执行期续租，队列空闲不写心跳；槽到期后新领取者使用新 token，旧执行者永远不能晚提交。
- 数据库忙、任务失败和资源暂停区分处理；FAILED 不在每次启动无限重试。
- 不借用 MarketDatasetUpdateLease 阻塞行情数据集，成就有独立任务锁。

### 11.4 2C2G 初始资源预算

以下是待目标机器验证的保守起点，不是已测试性能结论：

| 参数 | 建议起点 / 上限 |
| --- | --- |
| 成就执行并发 | 全局 1，包含预检查/校验/补算；一次最多一个在途处理 promise |
| 执行方式 | 默认复用应用进程的有界异步循环和共享 DB client，不新增常驻 Node / Prisma 进程 |
| 新增事实批次 | 默认 25 条，最多 100 条，优先于历史 |
| 历史事实批次 | 默认 100 条，硬上限 200；逐项读取，不能一次预取全部批次 |
| 用户发现分页 | 每次 10 个用户；按 metric 分组，不按徽章等级扩张 |
| 历史批次间隔 | 至少 250ms，遇压力退避 5 / 15 / 30 秒 |
| CPU 让出 | 每约 5ms 同步计算主动让出；不能只在数千条循环结束后让出 |
| 无任务发现 | 30 秒起，空闲退避到 60 秒；只查索引状态和必要水位 |
| 新事实唤醒 | 提交后合并唤醒，约 250ms 合并窗口；短批清空后回到低频发现 |
| 租约 / 续租 | 60 秒 / 15 秒；单批写预算远小于租约，续租失败即停 |
| 写入策略 | 每批仅一次事务尝试，等待与事务总时长目标 1500ms 内；明确失败交调度器退避，最多 3 次恢复；不复用 30 秒后台预算 |
| 单次 DB 等待 / 事务 | maxWait 起点 100ms、timeout 上限 1000ms；正常持锁目标 50ms 内，超出即减半后续批次 |
| 内存 | 单批显式读取/序列化数据不超过 4 MiB；成就模块稳定增量 RSS 目标不超过 64 MiB，必须实测 |
| 出错恢复 | 暂时性、明确回滚错误最多 3 次退避重试；提交不确定按第 10.3 节核实 |
| 详情查询 | 默认 20 条，服务端最多 100；Job 错误样本按第 8.1 节限额 |

实现注意：

- 不照搬当前聚合 worker 的 --max-old-space-size=1024；一台 2G 服务器还需运行应用、SQLite、系统及其他任务。默认不新增独立进程，只有同进程限时让出仍达不到前台延迟目标时，再实测受控短命 worker 的总 RSS 后决定。
- 同进程不代表可以运行长同步计算；纯计算按时间片让出，数据查询和写入均有限额。
- 同一轮调度只做有限工作，再重新检查优先级和资源，不能“处理直到全队列为空”占满事件循环。
- 成就后台事务使用现有 sqliteWriteTransaction，带 owner-qualified 第一条写语句、显式 writeFence 设置和成就专用短策略；不能通过替换 helper 降低原提交不确定保护。
- 现有写入封装只按剩余预算缩短 maxWait，不自动缩短显式 timeout。首版单批用 attempts=1；不能仅设置 budgetMs 就声称有硬时限。如果将来增加事务内多次尝试，每次 maxWait + timeout 及退避须受剩余总预算约束。无法确认 COMMIT 结果时，仍先读回核实，不进入普通自动重试。
- 不在持有事务时等待批次间隔，不加载完整行情或账户全部 fills。旧退出证据按有索引的周期范围分批读取；新退出分类使用第 8.2 节累积字段。
- 不引入 Redis、独立队列服务、规则脚本引擎或额外常驻监控进程。

### 11.5 资源门控与验证

- 每个历史批次前检查本机已有重任务状态；行情导入/聚合、交易纠错、PDF/AI 重任务明显竞争时延后历史批次，日常新增事实仍可持久化。只查询索引状态，不遍历整个任务历史。
- 根据可获得的真实部署指标限制压力：可用内存不足约 384 MiB、事件循环延迟持续升高（建议初始 P95 50ms）或前台写入连续忙时，暂停历史并退避，不丢任务/游标。
- 容器下应使用容器实际内存边界，不能用宿主机剩余内存冒充 2G 容器可用值；指标不可得时使用更保守批次和手动低峰启动，不无限重试。
- 记录应用 RSS、系统/容器可用内存、事件循环延迟、批次耗时、SQLite 锁等待及前台延迟。有限采样/环形汇总，不把每条事实打印成大量日志。
- 必须记录无补算基线，并在同一组数据/操作下比较新增捕获与补算中回放推进/下单 P50、P95、错误率和峰值总 RSS。
- 发布必须没有 OOM、swap 持续抖动或成就引发的前台 DATABASE_BUSY。建议将前台 P95 相比基线的退化目标控制在 20% 内；以目标机器实际结果评审，不把百分比写成已经达标的承诺。
- 若仍不满足目标，优先降批次/延长间隔、把首次补算安排低峰；不得为通过性能验收删除证据或放宽交易原子性。

## 12. 维护页面

### 12.1 路由和边界

- /admin：维护首页，仅链接本期成就维护。
- /admin/achievements：成就任务、预检查与异常详情。
- 首页、主导航、头像菜单和普通用户成就页均不提供维护页入口，直接输入地址访问。
- 隐藏导航不是鉴权。按照当前无登录设计，能访问应用的人可以直接访问这些路径。
- /admin 名称不引入管理员身份、密码或角色；本期不扩展权限或多租户。
- 维护页不含删除、清空成就、重置用户/账户、修改经验、数据库升级和手工授勋。
- 页面用中文“成就维护”，在页头说明“仅处理已有合格记录，不修改交易与资金”。

### 12.2 页面结构

1. 当前规则集 / 数据捕获启用时间 / 最近同步时间。
2. 总览：待处理、运行、已完成、失败、存在覆盖限制的用户/项目数。
3. 范围选择：全部用户或明确 userId，启用规则列表；显示实际作用范围，不只看浏览器当前用户。
4. 操作区：预检查、启动补算、重新校验、重试失败。
5. 任务列表：模式、范围、状态、处理阶段、已处理数量、时间及错误。
6. 详情：分页错误、覆盖限制、成功新增、跳过和重复命中数量。

### 12.3 操作含义

| 操作 | 行为 | 重复操作 |
| --- | --- | --- |
| 预检查 | 建立固定边界计划，输出预计差异，不写成就 | 返回同一在途计划或提示其进度 |
| 启动补算 | 执行服务端预检查计划，补齐未解锁阶段和进度；首轮历史默认在此启动 | 返回现有任务；范围相交时返回冲突，不重复排队 |
| 重新校验 | 按受影响指标在新代际重建并发布，保留已有解锁 | 与现有用户/指标范围相交时不可并发创建 |
| 重试失败 | 恢复特定失败项的同一计划与游标 | 已在运行则返回原任务 |

在最终“启动”按钮前清楚展示范围、规则、预计新增和不确定项，用户在当前页面明确点击即可，不叠加通用“确定吗”弹窗。普通状态反馈沿用 UI 规范。若后续引入不可逆操作，应单独设计，不能借本维护页默认放开。

关闭页面不中止任务；浏览器不承担计数与执行循环。服务关闭才中断执行，重新启动后按持久进度恢复。

### 12.4 状态

任务状态建议：QUEUED、RUNNING、SUCCEEDED、FAILED、INTERRUPTED。执行阶段另存，不混入状态枚举。

部分历史证据不足通过 coverage / 项目状态表达，不能把完成任务错误标成全部数据完整；详情应区分“已完成且有覆盖限制”和“执行失败”。
