# 自有资金账户部分提取与存入

日期：2026-10-26；基于用户已提交的 `1b48b33`，开始时工作区干净。状态：待用户验证。未提交、推送或部署到其他机器。

## 验收反馈与当前行为

本次替代首版“全额提取并归档”的简化：入口只在用户档案的“账户内资金”。每行提供“打开会话 / 提取资金 / 存入资金”，金额可手动输入，也可点“全部”。确认框明确本次数额，不自动归档或改变会话状态。

- 部分提取、全部提取均计入用户可用余额，并保留账户条目；全部提取后可再次存入。余额为 0 时可播放，不能开新仓；存入后恢复正常交易。
- 存入不超过该归属用户可用余额，提取不超过账户实际剩余资金。负账户余额如实显示，存入先覆盖已有亏损，可提上限最低为 0。金额大于 0、最多两位小数；前后端均检查，服务端负责最终事务校验。
- 延续空仓、无待成交订单、无进行中纠错的要求。手工归档会话可提取剩余资金，不能再存入；不会自动打开历史归档会话。此前旧版已结束结算的账户保留原状态。
- 只适用于归属用户的 TRAINING / STANDARD。实盘重演、未归属会话、自营公司账户不获得这些存取入口；自营出金仍走既有规则。全部用户仍是查看范围，存取归属以用户档案和会话所属者一致为准。
- 累计存入、累计提取按现有分配记录累加，每次存取均有账本流水。普通全提不设置 `settledAt`；该标志仅用于删除或重新开始时的最终结算，结算剩余金额而非重复返还已提取金额。

## 实现和统计边界

新增 `PaperTradingSession.cashAdjustment`，默认 0；迁移 `20261026170000_user_wallet_transfers` 与初始化脚本同步。独立于原币种字段，不改变初始本金、交易已实现盈亏或手续费。已有字段和原数据不回填、不重算。

实际账户余额 = 初始本金 + cashAdjustment + 已实现盈亏 − 手续费。存取在分结算边界处理舍入；不会通过改写交易盈利来凑余额。交易净盈亏与回撤排除外部资金流，既有峰值和历史回撤不因提取产生虚假亏损。普通推进、空仓快速推进、客户端推演、快照和检查点均保留该调整；无现金调整时维持原行为。

用户、金额、方向、会话版本、账户状态及资金条件在同一写事务校验；钱包、分配记录、账户资金、已揭示位置的权益点、命令和检查点一并提交。`TRANSFER:会话:请求ID` 唯一来源确保重复请求只记一笔，复用 ID 更改方向/金额报冲突。`CASH_TRANSFER` 命令重放只恢复账户状态，不重复记账。训练仍禁止时间回退，不扩大实盘重演能力。

删除与重新开始继续做最终结算，读取包含现金调整后的剩余资金，保留原有显式删除确认和自营费用规则。

日常入口 `http://localhost:3000/users`，使用 `.env` 对应的本机 `prisma/dev.db`；本次只读基线为 1 用户、1 钱包、2 流水、1 分配、1,000 笔交易、1 行情、1 回放会话及账户。本次已完成升级和只读核对。新增现金调整默认为 0，以上数量及所有原字段完整校验一致，未在此库进行资金操作或测试交易。

独立合成入口 `http://localhost:3105/users` 使用 `tmp/user-wallet/acceptance.db`，头像目录独立，关闭同步。沿用已构造的三个合成用户与 TEST 行情，已有样例不清空。启动 `corepack pnpm run acceptance:user-wallet`；开发可追加 `--dev`。日常启动 `corepack pnpm start`；切换 dev/start 前先停止并完成 `corepack pnpm run build`。

1. 打开“余额验收·资金存取 → 账户内资金”，应看到提取和存入两个按钮。记录当前余额，提取 245 USDT：用户可用余额增加 245、账户余额减少 245，会话保持 ACTIVE。
2. 再点提取，点“全部”后确认：账户余额为 0，条目保留、存入可用。打开会话可播放，开新仓应提示先存入。
3. 从用户档案存入 245 USDT：用户余额减少 245，账户余额增加 245，可继续原会话交易。金额超过用户余额、超过可提余额、0、负数或小数超过两位不能成功。取消确认不产生流水。
4. 在账本检查每次存取独立记账；交易盈亏、费用、交易数量、已获成长不因存取改变。另一个用户的余额不能被用于此账户。
5. 手工归档后的账户只能提取；实盘重演、未归属和自营公司账户不出现普通存取入口。删除/重新开始只结算尚未提取的剩余金额，不重复入账。

合成样例会因上述确认操作改变，后续以当前账户及账本为准，不重复假设初始演示值。
