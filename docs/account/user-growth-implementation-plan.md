# 用户档案与修仙成长体系：分阶段开发计划

制定日期：2026-10-25。

需求依据：[用户档案与修仙成长设计](user-growth-design.md)。本计划安排开发顺序和验收方式，不代表已执行迁移或通过验收。2026-10-25 用户已指示提交第一阶段并进入第二阶段，第一阶段记为已确认；第一阶段已提交为 `4e2ba86`，第二阶段已完成独立副本实现与检查，停在待用户验证，第三至第五阶段未开始。实际变更、检查和未接入范围见[第一阶段交付记录](user-growth-stage-1-progress.md)及[第二阶段交付记录](user-growth-stage-2-progress.md)。

## 1. 实施方式

采用五个阶段，每阶段交付一个可验证的结果。先验证视觉方向，再验证用户归属，随后接入经验与自营成果，最后完成头像和整体回归。

- 每完成一阶段，先由开发者完成本阶段适用的自动检查，再提供可打开的验收入口、操作步骤、预期结果及未实现范围。
- 交付后停在“待用户验证”，由用户试用并提出调整。收到用户明确通过或继续下一阶段的指示后，才进入下一阶段；不能完成一阶段后自动连续开发全部功能。
- 用户反馈影响本阶段时，先修正并复验。纯视觉调整留在对应组件，不为改配色或构图重写归属、成长和撮合逻辑。
- 每阶段记录实际变更、检查命令及结果、用户反馈与处理。计划中的检查不是已通过的证据。
- 后续检查由 `tester` 协助执行相关测试、lint 与类型检查，主开发负责修正问题及浏览器视觉验收；记录通过、失败和未运行项目，不因测试代理参与而省略实际证据。
- 开发及验收优先使用独立实例和验收数据库；正式使用中的行情、会话与交易不用于试验删除、归属、出金或突破。验收数据不自动并入正式数据。
- 前四阶段用于增量验收，正式数据库升级与完整功能交付集中在第五阶段处理；不能因用户试用预览就自动升级日常使用的数据库。

### 阶段总览

| 阶段 | 主要交付 | 用户本次重点验证 | 状态 |
| --- | --- | --- | --- |
| 1 | 用户界面可交互预览 | 风格、布局、修仙元素、各境界展示 | 已确认 |
| 2 | 用户档案、选择记忆、会话归属与历史归属 | 切换是否清楚，数据归属是否正确 | 待用户验证 |
| 3 | 交易与逐笔复盘经验、独立成长记录、炼气升级 | 奖励是否正确且不重复，删除是否保留成长 | 待开始 |
| 4 | 自营成果、六项条件、筑基突破 | 跨会话/轮次计数、实得金额与突破判定 | 待开始 |
| 5 | 正式头像、体验完善、整体回归与升级交付 | 完整流程、兼容性、最终视觉 | 待开始 |

### 规则基线

已确认的需求按设计文档执行。经验数值、18,100 累计经验、1,200 个持仓周期、600 笔逐笔复盘及部分交互仍沿用文档中的 V1 建议参数，开发时集中配置并记录版本；不把它们误称为用户逐项确认的固定值。用户在阶段验收中调整参数时，同步文档和测试，不静默重算已结算历史。

以下要求贯穿所有阶段：无登录和权限；默认全局；历史归属不参与成长；同一笔逐笔复盘只奖励一次；删除来源不撤销已结算成长；任意自营模板均可；考核 ≥20 次、出金 ≥10 次、分成后实得 ≥100,000 USDT；没有三个月或练习天数等硬性限制。

## 2. 第一阶段：用户界面预览，先确定视觉方向

### 开发范围

- 按设计文档第八节制作独立验收入口，复用未来实际页面组件，数据通过明确的展示输入提供，避免预览通过后另写一套页面。
- 展示用户切换入口、档案列表、档案身份区、境界轨迹、本段经验、六项突破条件、成长流水与会话列表；最近仅展示 5 条，完整历史每页 20 条，不按条数删除历史。
- 展示创建/编辑资料、历史归属、头像选择/裁切的交互布局；本阶段只模拟保存反馈，不写入真实用户、会话或成长数据。
- 采用“浅纸、墨字、细线、玉色”的修行档案方向，重点确认构图、留白、信息层级和修仙元素的分量。
- 提供固定演示状态：凡人 0 经验、凡人接近 100、炼气中段、十二层缺条件、全部条件满足、筑基一层，以及加载、空数据和失败状态。
- 展示“当前选择”和“会话归属”不同、查看他人档案、历史归属不参与成长等容易混淆的场景。
- 头像先使用可替换的占位图；如需生图验证画风，仅制作少量样稿，整套正式素材留待第五阶段。

预览状态切换和演示数据只用于验收，不成为正式页面修改经验、调整境界或伪造出金的入口。本阶段不修改数据库、撮合和现有业务流程，不将模拟结果显示成真实奖励。

### 开发者检查

- 运行 lint 和必要类型检查，不为纯装饰编写镜像式测试。
- 按桌面 UI 规范检查 1280px、1440px、1920px 和短高度窗口的布局；交付时记录实际检查方式，未进行浏览器视觉验收不得声称通过。
- 检查本段经验与累计经验没有混用，凡人不分层，筑基一层没有虚构下一层目标，六项条件不平均为总百分比。
- 检查键盘、焦点、长昵称、大金额、弹窗滚动及减少动画状态。

### 用户验收

1. 打开预览，依次查看凡人、炼气、突破准备、可突破和筑基状态。
2. 判断整体是否与系统协调，修仙元素是否足够，是否需要改布局、色彩或头像方向。
3. 切换演示用户、打开他人档案，确认能区分正在选择谁、正在查看谁、会话属于谁。
4. 打开资料和历史归属弹窗，查看选择、取消、错误与空状态是否清楚。

**阶段结束条件：** 用户认可主要视觉方向、页面布局和交互路径；小范围配色与素材仍可后续微调。交付后等待用户验证，不直接开始数据接入。

## 3. 第二阶段：接入用户档案和会话归属

### 开发范围

- 实现用户创建、昵称修改、列表与档案读取，先使用默认头像；正式上传和整套预制素材放在第五阶段。
- 接入全局及回放工具栏中的用户选择，浏览器保存选择；读取失败保留已知选择，ID 确认失效才回到全局。
- 接入个人会话筛选，保持行情和基础资源共享；已有链接可直接访问其他人的会话，不引入权限检查。
- 普通新建会话在提交时固定归属；“重新开始”和“重新考核”按设计文档继承表处理。
- 在用户档案中实现历史会话选择与全批原子归属，清楚标记不参与成长；不在原回放和日志中增加历史归属操作。
- 接入第一阶段页面的真实用户与会话数据。成长区域尚未接入的范围在阶段交付说明中注明，不展示第一阶段的虚构经验为真实数据。

### 数据结构先建立完整基础

本阶段设计并在验收库实现用户档案、会话归属/资格，以及后续需要的独立成长事实、累计数据、来源唯一键、规则版本和境界记录基础。奖励业务在第三、四阶段分别接入，不在此阶段补算历史。

同步 Prisma 迁移与 `scripts/init-sqlite.mjs`，在隔离副本验证两种安装路径；目标实际采用哪种路径须按[升级指南](../operations/upgrade.md)核实，不能在同一安装中混用来绕过错误。旧会话保持未归属，旧行情、进度、账户、成交与复盘保留。

前两阶段尚不能用于承诺日常成长结算。在独立验收环境验证；开始第三阶段时记录成长接入边界，不把第二阶段产生的试验交易当成已经完整结算或自动回溯奖励。

### 开发者检查

- 补充用户校验、归属固定、筛选、并发归属、继承规则及数据库升级的有意义测试；执行相关 Vitest、lint 和必要类型检查。
- 在数据库副本比较升级前后原业务字段、数据量和外键完整性，确认未补发历史成长。
- 覆盖当前选择改变、双标签或旧请求返回、提交期间用户变化、网络失败和浏览器存储不可用。
- 对普通新建、成长/历史归属/未归属会话“重新开始”、自营“重新考核”逐项验证。
- 验证普通 HTTP，包含 `crypto.randomUUID` 不可用的环境。

### 用户验收

1. 不创建用户，以“全部用户”打开原有流程，确认仍可使用全部数据。
2. 创建两个用户，分别建立训练会话，切换和刷新，查看范围与浏览器记忆是否正确。
3. 打开甲的会话，再选择乙，确认原会话归属仍为甲，已有交易状态未变化。
4. 在甲的档案选择未归属历史会话，确认归属后可找到，且明确不参与成长。
5. 按准备好的样例检查“重新开始”和“重新考核”的归属继承。

**阶段结束条件：** 用户可稳定创建、选择、查看档案，归属与历史处理正确，原业务数据及全局体验保留。交付后等待用户验证。

## 4. 第三阶段：接入日常经验与炼气升级

### 开发范围

- 在独立业务模块实现经验及境界纯规则，使用当前 V1 建议参数：完成周期 +5、首次逐笔复盘 +10。
- 接入完整持仓周期结算，不把分批成交或 FIFO 日志拆行多算为周期。
- 接入逐笔复盘保存，在服务端判定非空内容变化或可验证的显式 AI 采用，首次完成只奖励一次；不新增会话/阶段复盘奖励。
- 将成长事实与累计可靠保存，覆盖请求重试、并发、失败回滚及来源唯一键。先完成这一基础，再依此接入自营事件。
- 实现凡人 0 经验、100 自动炼气一层、炼气各层升级和十二层经验继续累计；筑基突破功能留到第四阶段。
- 档案显示真实累计、本层进度、成长流水和轻量操作反馈；自营尚未接入的范围在交付说明中明确，不以缺少临时接入误导用户为真实历史零成果。
- 删除原会话后保留已结算经验、复盘数、周期数及来源摘要；根据历史结算值可重建累计。

本阶段只接入交易和逐笔复盘来源，自营经验与成果的完整结算在第四阶段完成。阶段测试不改变正式阈值、不提供正式用户手动加经验功能。

### 开发者检查

- 补充纯规则、SQLite 集成和相关 API 测试；执行相关 Vitest、lint 和必要类型检查。
- 覆盖 99/100、399/400、13,600、18,100 等边界和一次奖励跨多层；验证计算使用累计经验而非显示文字。
- 覆盖同一周期多笔日志、重复复盘、空白、自动预填、显式 AI 采用、保存冲突、并发与请求重试。
- 覆盖归档训练补复盘，以及未归属、历史归属、实盘重演的排除资格。
- 删除来源后复核累计、去重和重建结果；新规则版本不能重算旧奖励。
- 对接入前后同样的合法交易操作比较原撮合、账户、费用、订单和关卡结果，成长不得改变它们。

### 用户验收

1. 在具备成长资格的新训练会话完成一个持仓周期，查看增加 5 经验。
2. 为一笔交易编辑并保存复盘，查看再增加 10 经验；重新编辑或清空重填，不再增加。
3. 查看准备好的边界样例，确认凡人晋升、炼气升层及本段进度显示正确。
4. 对照历史归属、未归属与实盘重演会话，确认操作仍可用，但不产生个人成长。
5. 仅在可删除的验收会话上验证删除，确认经验、累计数量和来源摘要保留。

**阶段结束条件：** 日常奖励准确、稳定、不重复，炼气升级可解释，成长独立于原会话保存。交付后等待用户验证。

## 5. 第四阶段：接入自营成果和筑基突破

### 开发范围

- 消费现有自营账户成功晋级事件和成功出金流水，复用原规则结果，不重写考核/出金判定或再次扣款。
- 实现每轮考核通过 +100、每轮首次出金 +200；该轮后续出金只增加次数与实得，不重复发首次奖励。
- 跨会话、跨账户轮次累计考核和出金；相同轮次多次出金全部计入突破次数，任意模板均可。
- 按分成后 `received` 累计 USDT 实得；成长金额仅记录 USDT，不建立其他币种金额累计或分币种详情，不按 USD 等价折算；现有账户的币种设置不在第一阶段修改。
- 接入六项条件、缺口展示、“突破筑基”操作、成功记录、重试与幂等；无时间门槛。
- 实现筑基一层的已达成状态，后续层级待开放，仍继续记录经验和成果。
- 复核自营会话或相关数据删除后，已结算成果及突破结果保持不变。

### 开发者检查

- 补充自动/手动晋级、跨会话跨轮次、同轮多次出金、首次奖励去重、金额精度及突破边界测试；执行相关 Vitest、lint 和必要类型检查。
- 验证源事件与关联流水不会同时被计两次；预览、失败操作、回滚、并发和重试不增加成长。
- 分别验证恰好 20 次考核、10 次出金、100,000 USDT 实得，以及每项少一点的情况。
- 申请金额达标但实得不足、其他币种金额或界面取整均不能代替实得条件。
- 六项只要有一项不足不能突破；全部满足即使不足三个月也能突破，重复提交只有一次达成结果。
- 原自营账本、资金、回撤、关卡、交易及轮次行为与接入前一致。

### 用户验收

1. 在准备好的自营验收账户完成晋级，查看通过次数和经验变化。
2. 本轮首次出金查看 +200 经验、次数 +1 和实际 `received`；后续出金再次计数及金额，但不再奖励 +200。
3. 切换不同会话或轮次，确认成果累计到同一用户；检查当前选择改变不会把成果给错人。
4. 使用接近门槛的验收样例，查看不同缺口；完成最后一个真实操作后验证“可突破”与筑基一层。
5. 删除可删除的验收来源，确认已累计成果与已取得境界保留。

临界样例由独立测试数据准备，通过结算服务构建可解释的成长事实。不得降低正式规则来快速验证，也不要求用户亲自重复 20 次完整考核或在真实使用账户上试验失败和重置。

**阶段结束条件：** 自营成果、金额与突破判定均正确，可完成从凡人到筑基一层的闭环。交付后等待用户验证。

## 6. 第五阶段：头像、体验完善与正式交付

### 开发范围

- 按第一阶段认可的画风生成正式预制头像，暂按 8 个建议数量执行；接入选择、替换和失败占位。
- 实现头像上传、格式/大小/尺寸校验、裁切预览、键盘调整、服务端重新编码与保存；取消或失败保留原资料。
- 调整用户反馈中的局部视觉、文案、菜单和弹窗细节，检查主题样式不影响其他业务页面。
- 完整检查全局/个人范围、继承、历史归属、日常经验、自营成果、删除保留和筑基全部流程。
- 整理最终设计、规则版本、迁移和操作说明。更新功能文档时，仅标记已经实际实现及验证的内容。

### 开发者检查

- 执行完整 `corepack pnpm lint`、`corepack pnpm test` 和 `corepack pnpm run build`；如遇 Windows Prisma 占用，核对后仅停止本项目相关进程并顺序重试。
- 完成设计文档第八节的桌面检查清单，包含 1280px、1440px、1920px、短高度、长昵称、大金额、键盘和减少动画；记录实际完成的检查及例外。
- 验证普通 HTTP / 局域网访问、`crypto.randomUUID` 不可用、图片失败及上传失败。
- 回归原训练、实盘重演、账户轮次、回放推进、复盘、导出和共享资源，确认没有扩大用户筛选范围或改变原业务规则。

### 数据升级与交付

按[升级指南](../operations/upgrade.md)核实实际数据库、运行方式、迁移历史及原密钥；正式升级前完成一致性备份和数据库副本演练。保留原日志模式并沿实际安装路径迁移，校验完整性、外键及原行情/会话/账户/复盘，不重置数据库或清空数据卷。

交付须说明目标代码、迁移路径、备份位置、自动检查结果、仍未验证的内容与服务状态。不得从历史文档推断本机当前已备份或已升级，也不得用升级前备份覆盖验收后新增的真实交易来“回退”。

### 用户最终验收

1. 选择预制头像，再上传自选图片，确认列表、顶部入口与档案一致，取消和失败能保留原头像。
2. 从全局使用开始，创建/选择用户，建立训练会话，完成交易、逐笔复盘和自营成果，查看成长及突破。
3. 检查已有业务数据、原交易入口和不创建用户时的体验。
4. 确认最终界面风格与实际使用反馈均已落实；未开放境界标识正确。

**阶段结束条件：** 用户确认完整体验，必要检查完成，数据升级与交付证据齐全。若未执行正式升级，应明确报告为“验收完成、尚未升级正式实例”，不能宣称已部署。
