# UI 开发规范

本文档是本项目唯一的 UI 设计与实现规范。凡新增页面、组件或修改任何用户可见界面，开始开发前必须完整阅读本文档，完成后必须执行文末对应检查清单。

规范约束新增和修改部分，不要求为了顺手统一而改动无关旧界面。若业务需求确实需要例外，应在代码或交付说明中写明原因、影响范围和验证方式；同类例外出现两次及以上时，应优先沉淀为 `components/ui/` 基础组件或更新本文档。

## 1. 产品视觉基线

- 默认语言为简体中文，整体是浅色、紧凑、专业的交易分析工具，不使用营销站式的大面积装饰、渐变或夸张动效。
- 蓝色表示主要操作、当前选择和导航；Slate 表示背景、边框和中性文字；绿色表示盈利或成功；红色表示亏损、错误或危险操作；琥珀色表示警告和需要注意的状态。
- 信息层级依靠标题、间距、边框和字重共同建立。颜色不能成为传递状态的唯一方式，必须同时有文案、图标、符号或位置语义。
- 业务页面优先保证数据可读、操作可预测和高信息密度，再考虑装饰效果。
- 现有 `app/globals.css`、`tailwind.config.ts` 和 `components/ui/` 是实现层的基线。本文档与代码不一致时，新增界面以本文档为目标，并在基础组件中集中修正，不在业务页面制造新的变体。

## 2. 设计基础

### 2.1 颜色

优先使用 Tailwind 中已经映射的语义色，而不是在业务组件中新增任意色值：

| 用途 | 首选类或色阶 | 使用规则 |
| --- | --- | --- |
| 页面背景 | `bg-background` | 全局浅灰背景 |
| 主表面 | `bg-card`、`bg-white` | 卡片、表格、弹窗和浮层 |
| 主文字 | `text-foreground`、`text-slate-950` | 标题和关键值 |
| 次要文字 | `text-muted-foreground`、`text-slate-600` | 说明和辅助信息 |
| 弱化文字 | `text-slate-500` | 元数据、时间和提示，不承载关键结论 |
| 边框 | `border-border`、`border-slate-200` | 常规分隔和容器轮廓 |
| 主要操作 | `bg-primary`、`text-blue-700` | 主按钮、链接、选中项 |
| 成功 / 盈利 | `emerald-50/200/700` | 成功反馈、正收益 |
| 错误 / 亏损 / 危险 | `red-50/200/700`、`destructive` | 错误反馈、负收益、删除操作 |
| 警告 | `amber-50/200/800` | 不完整数据、风险提示 |

- 新增全局颜色语义时，先更新 CSS 变量和 Tailwind 映射，再由基础组件使用。
- 禁止新增无语义的十六进制颜色、相近但不同的蓝色或临时渐变。
- 图表可以使用独立序列色，但同一业务含义在所有图表中必须保持一致，并保证浅色背景下可辨认。

### 2.2 字体和数据

- 页面主标题：标准内容页使用 `text-3xl font-semibold tracking-tight text-slate-950`；首页主标题可使用 `text-4xl`；全屏工作区为节省空间可使用 `text-xl`。
- 区块标题：主要区块使用 `text-2xl font-semibold tracking-tight`，卡片标题统一使用 `CardTitle` 的 `text-base font-semibold`。
- 正文和表单：默认 `text-sm`；页面说明通常为 `text-sm text-slate-600`；元数据和补充说明使用 `text-xs text-slate-500`。
- Eyebrow：统一使用 `font-mono text-sm uppercase tracking-wide text-blue-700`。
- 金额、百分比、R 倍数、价格、数量和时间序列值使用 `tabular-nums`；需要强调代码、序号或精确数据时可增加 `font-mono`。
- 不使用小于 `text-xs` 的字号，图表内空间受限的辅助标注例外可使用 `text-[11px]`，但不得承载关键操作或唯一说明。

### 2.3 间距、圆角和阴影

- 标准页面区块间距使用 `space-y-6`，首页等展示型页面可使用 `space-y-8`。
- 卡片之间使用 `gap-3` 或 `gap-4`，大型并列区域使用 `gap-6`；表单字段内部使用 `space-y-2`，表单分组通常使用 `space-y-4`。
- 标准卡片内边距为 `p-5`，紧凑工具区可使用 `p-3`，空状态使用 `p-6`。不要为相邻同级卡片随意混用内边距。
- 控件使用 `rounded-md`，卡片和主要容器使用 `rounded-lg`。除特殊浮层外，不新增更大的圆角风格。
- 普通卡片使用 `shadow-sm` 或无阴影；菜单、弹窗和浮动面板可使用 `shadow-lg`、`shadow-xl` 或 `shadow-2xl`。禁止用重阴影装饰普通内容区。
- 图标默认尺寸：按钮和行内操作为 `h-4 w-4`，卡片或区块图标为 `h-5 w-5`。图标必须来自 `lucide-react`，不混用其他图标风格。

## 3. 页面结构

页面内容顺序统一为：面包屑 → 页面标题区 → 页面级操作 → 主内容 → 次要说明。页面级主操作放在标题区右侧；窄屏时移到标题下方并允许换行。

### 3.1 标准内容页

适用于数据集、模拟、基础数据和普通列表页：

```tsx
<div className="space-y-6">
  <Breadcrumbs items={items} />
  <section className="flex flex-col gap-4 border-b pb-6 md:flex-row md:items-end md:justify-between">
    <div>
      <p className="font-mono text-sm uppercase tracking-wide text-blue-700">...</p>
      <h1 className="text-3xl font-semibold tracking-tight text-slate-950">...</h1>
      <p className="mt-2 max-w-3xl text-sm text-slate-600">...</p>
    </div>
    <div className="flex flex-wrap items-center gap-2">...</div>
  </section>
  ...
</div>
```

- 使用 `app/layout.tsx` 提供的 `max-w-7xl px-6 py-8` 页面容器，不再嵌套另一个随意宽度的普通页面容器。
- 标题区没有操作时可以省略横向布局，但仍保留 `border-b pb-6`。
- 首页 Hero、报告摘要等已有明确目的的结构可以例外，但内部视觉层级仍遵守本规范。

### 3.2 宽表格页

适用于交易日志等需要展示大量列的页面：

- 仅数据工作区突破标准容器，优先复用现有 `max-w-[1800px]` / `max-w-[2200px]` 宽度模式。
- 面包屑、标题和主要操作仍保持标准页层级，不因表格较宽而改变字号或按钮样式。
- 表格自身负责 `overflow-x-auto` 和合理 `min-width`，禁止让整个页面产生横向滚动。
- 关键识别列或操作列可固定，但必须通过背景、边框和阴影明确层级，并验证横向滚动时不遮挡内容。

### 3.3 全屏 K 线工作区

适用于 `/market-replay/[id]` 一类以图表和连续操作为核心的页面：

- 可以隐藏全局 Header、突破 `max-w-7xl` 并使用视口高度，但必须保留返回路径、数据集身份和当前工作上下文。
- 顶部信息区保持紧凑，图表区域使用剩余高度；底部播放控制和浮动交易面板不得挤压图表到不可用尺寸。
- 视口宽高计算必须使用 `dvh` 并保留安全边距；浮层必须限制最大宽高并允许内部滚动。
- 工作区的密集控件可以使用 `h-8` / `h-9`，但仅限桌面高频工具栏；主要提交、危险操作和窄屏操作仍使用标准尺寸。

## 4. 组件与控件

### 4.1 复用优先级

1. 先使用 `components/ui/` 中已有的 `Button`、`Input`、`Textarea`、`Select`、`Card`、`Table`、`Alert`、`Badge`、`Dialog`、`ConfirmDialog` 和 `DatePicker`。
2. 已有组件能力不足时，优先为基础组件增加明确、可复用的 variant 或属性。
3. 只有图表画布、菜单项、拖拽句柄、开关等特殊交互允许直接使用原生元素；相同模式出现两次时必须抽成基础组件。

禁止在业务组件里复制一整套按钮、输入框、表格或弹窗样式。禁止使用浏览器原生 `alert`、`confirm` 和 `prompt`。

### 4.2 按钮和操作层级

- 每个独立操作区最多一个 `default` 主按钮。
- `secondary` 用于次要但常用的操作；`outline` 用于普通辅助操作；`ghost` 用于低强调度或工具栏操作；删除及不可逆操作使用 `destructive`。
- 普通按钮使用 `h-10`，紧凑列表和工具栏使用 `size="sm"`，只有图标时使用 `size="icon"` 并提供 `aria-label`。
- 用作链接的按钮必须使用 `Button asChild` 包裹 Next.js `Link`，不要复制按钮 class。
- 提交期间禁用重复触发，显示旋转图标或清晰的进行中文案；原按钮宽度尽量保持稳定。

### 4.3 表单

- 每个字段必须有可见 `Label` 并通过 `htmlFor` 与控件关联；仅在空间确实不允许时使用 `sr-only` 标签。
- 输入、选择和文本域默认占满所在列，标准高度 `h-10`。同一行字段必须有一致的标签位置和控件高度。
- 帮助文字放在控件下方，使用 `text-xs text-slate-500`；校验错误紧邻字段，使用 `text-xs text-red-600`，并通过 `aria-describedby` 关联。
- 必填、单位、允许范围和格式在提交前可见，不依赖失败后才说明。
- 表单底部操作右对齐并使用 `flex justify-end gap-2 border-t pt-4`；取消在前、主操作在后。

### 4.4 卡片、表格和数据展示

- 卡片使用 `CardHeader` / `CardTitle` / `CardDescription` / `CardContent`，不要在业务页面重新拼装同样的边框、圆角和内边距。
- 表格优先使用 `components/ui/table.tsx`。列标题简短、左对齐文本、右对齐数字；同列的小数精度保持一致。
- 行操作放在最右侧，常用操作可见，低频操作进入菜单；危险操作不能与主操作使用相同视觉权重。
- 空值统一显示 `copy.common.dash` 等产品约定，不混用空字符串、`N/A`、`null`。
- Badge 只表达短状态或分类，不放长句，也不代替按钮。

### 4.5 弹窗、菜单和浮层

- 普通表单或详情使用 `Dialog`，确认删除使用 `ConfirmDialog`。若现有组件缺少所需的焦点或尺寸能力，应在 `components/ui/` 中补齐。
- 弹窗必须有标题；必要时增加说明。关闭按钮要有 `aria-label`，支持 Escape，打开后锁定背景滚动并正确管理焦点。
- 弹窗默认最大宽度 `max-w-2xl`，确认框 `max-w-md`，最大高度不超过 `calc(100dvh-2rem)`，内容区内部滚动。
- 菜单、Tooltip 和 Popover 不得超出视口；只在 hover 出现的关键信息必须同时支持键盘焦点或点击查看。

## 5. 状态与反馈

所有异步区域至少处理加载、成功、空数据和失败四种状态；涉及权限、条件或长任务时再处理禁用、警告和进度状态。

- **加载：** 保留原布局，禁用触发控件，使用 `animate-spin` 图标或局部骨架；区域可设置 `aria-busy="true"`。不要用全页空白替代局部加载。
- **空状态：** 在原内容边界内使用虚线或普通边框、`p-6`、简短原因和一个明确下一步；没有可执行动作时不要伪造按钮。
- **成功：** 使用绿色 Alert 或就地反馈，并设置 `role="status" aria-live="polite"`；不为普通保存成功弹出阻塞式弹窗。
- **错误：** 使用红色 Alert 或紧邻相关字段的错误文本，说明发生了什么以及如何恢复；需要立即播报的错误使用 `role="alert"`。
- **警告：** 使用琥珀色，明确风险或不完整之处，但不与错误、删除混用。
- **禁用：** 只有确实不可用或正在提交时禁用，并在上下文中解释原因；不能只通过降低透明度让用户猜测。
- **危险操作：** 使用 destructive 按钮和 `ConfirmDialog`，确认文案必须明确对象与后果，加载时禁止关闭和重复确认。
- **长任务：** 展示当前阶段、进度或已处理数量；允许失败后恢复时提供重试入口，不用虚假的匀速进度。

## 6. 交易与图表语义

- 正收益、盈利交易和成功成交使用绿色；负收益、亏损交易和危险风险使用红色；零值保持中性。
- 买卖方向不应只依赖颜色，必须同时显示“买入 / 卖出”、方向图标或明确符号。若特定图表已有稳定的买卖配色，保持该模块内部一致。
- R 倍数、收益、回撤和资金数值必须标明单位或通过列标题、Tooltip 给出语境；正负号和小数精度保持稳定。
- 图表必须提供标题、图例或直接标签、Tooltip 和无数据状态；颜色较多时避免相邻序列过于接近。
- 图表容器必须响应宽度并有明确最小高度。高密度图表可隐藏次要标签，但不能隐藏关键风险结论。
- K 线回放中的形成、不完整、成交、持仓和订单状态沿用现有语义，不创建另一套相冲突的标记。

## 7. 响应式与可访问性

### 7.1 响应式

- 从窄屏开始保证内容可读，再用 Tailwind 的 `sm`、`md`、`lg`、`xl` 增强布局。
- 多列网格在窄屏降为单列；标题操作区允许换行或纵向排列；不要仅缩小字体来塞入内容。
- 页面主体不得横向滚动。宽表格、图表工具栏和代码内容应在自己的容器内滚动。
- 标准控件和主要操作保持至少 40px 高；触控密集区域优先 44px。`h-8` / `h-9` 仅用于桌面高密度工具区，并保持足够间距。
- 至少验证 375px 窄屏和 1440px 桌面；宽表格或工作区额外验证 1280px 与 1920px。

### 7.2 可访问性

- 使用正确的 `header`、`nav`、`main`、`section`、`form`、`table`、`button` 等语义元素，不用可点击 `div`。
- 所有交互可通过键盘完成，并使用统一的 `focus-visible:ring-2 focus-visible:ring-ring` 焦点样式。不得移除焦点而不提供替代。
- 图标按钮必须有中文 `aria-label`；装饰图标使用 `aria-hidden="true"` 或不重复可见文字。
- 表单错误、异步状态和弹窗按本规范设置 ARIA 关联；表格列标题使用 `th`。
- 文本与背景保持可读对比度。浅色状态背景使用对应的深色文字，弱化文字不能用于关键数字和主要操作。
- 尊重系统减少动画偏好；动画只用于状态变化和方向提示，不影响用户完成操作。

## 8. 文案与数字格式

- 所有用户可见的固定文案先加入 `lib/i18n.ts`，组件通过 `copy` 读取。不要在 JSX、Toast、错误分支或 `aria-label` 中散落大段中文。
- 默认语言是 `zh-CN`。按钮使用清晰动词，标题说明对象，错误文案说明恢复方式；避免“确定吗？”等缺少上下文的表达。
- 金额、常规数字和百分比分别优先使用 `lib/format.ts` 的 `formatMoney`、`formatNumber`、`formatPercent`。
- 日期时间明确时区语境，并使用项目统一 locale；表格中相同类型数据必须采用相同格式。
- 中文与英文、数字之间保持可读空格，如“EMA 20”“风险 1.00%”“共 100 笔交易”。

## 9. 推荐与禁止示例

推荐：

```tsx
<Button asChild variant="outline" size="sm">
  <Link href={href}>{copy.home.open}</Link>
</Button>

<Alert className="border-red-200 bg-red-50" role="alert">
  <AlertTitle>{copy.common.error}</AlertTitle>
  <AlertDescription>{error}</AlertDescription>
</Alert>
```

禁止：

```tsx
<a href={href} className="rounded bg-[#2878ff] px-[13px] py-[7px]">打开</a>

if (window.confirm("确定吗？")) {
  // 删除
}
```

原因：前者绕过 Next.js Link、Button 体系和设计 token；后者缺少对象与后果说明，并破坏统一弹窗体验。

## 10. 开发与审查检查清单

### 新页面

- [ ] 使用正确的标准页、宽表格页或全屏工作区结构。
- [ ] 包含面包屑、统一标题层级和唯一主操作。
- [ ] 优先复用 `components/ui/`，固定文案已加入 `lib/i18n.ts`。
- [ ] 加载、空、成功、错误、禁用和危险操作状态已按实际流程处理。
- [ ] 已验证键盘操作、焦点、ARIA、375px 和 1440px；数据密集页已验证额外宽度。

### 修改现有页面

- [ ] 修改部分遵守本文档，且没有顺手改动无关旧界面。
- [ ] 没有新增重复控件、任意颜色、任意尺寸或原生阻塞弹窗。
- [ ] 不破坏现有响应式布局、滚动区域、图表尺寸和数据格式。
- [ ] 新增可见文案、错误状态和异步反馈均已纳入统一体系。

### 代码审查与交付

- [ ] 视觉层级、操作层级和业务颜色语义一致。
- [ ] 基础组件可以覆盖的样式没有散落在业务组件中。
- [ ] `corepack pnpm lint` 通过；复杂交互的相关测试通过。
- [ ] 完成必要尺寸的视觉检查，并在交付说明中记录例外及原因。
- [ ] 若同类例外已重复出现，已抽象基础组件或同步更新本规范。
