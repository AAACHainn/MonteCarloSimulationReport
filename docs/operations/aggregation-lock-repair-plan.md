# 聚合排队与 SQLite 写入冲突修复方案（v3.1，已独立复核通过）

> 文档状态：设计与计划。适用范围：聚合排队与 SQLite 写入冲突的方案及后续实施背景；文末已有实施记录，审核结论不替代当前测试，也不表示仍需从头实施。
> 当前规范：[时间聚合与查询](../market-data/time-aggregation.md)、[升级指南](upgrade.md)。

本方案替代旧版“不同数据集的构建 worker 可以并行”的选择。目标是独立聚合构建任务全局串行排队，前台回放、绘图、复盘、交易日志和 AI 对话继续使用；前台只可能等待短批次写事务，不等待整个聚合任务结束。

本文最初作为方案完成独立审核，用户授权实施后已实现相应代码；实施记录见文末。设计审核与代码复核不替代实际测试结果。

## 1. 问题依据与范围

已在隔离数据库、项目当前 Prisma / better-sqlite3 / WAL / FULL 路径复现：事务 A 先读取，连接 B 写入调度心跳并提交，A 随后的 `marketAggregatedBar.createMany()` 返回 `SQLITE_BUSY_SNAPSHOT`。结束旧事务并开启新事务后可以成功。历史报错的具体竞争写入者无法唯一确定，两个构建任务、同步心跳或其他业务写入均可能参与。

仅串行构建仍不足以消除构建与其他业务写入之间的冲突，因此采用三部分：持久化构建队列、聚合写前取得写入资格及完整事务重试、相关前台写事务的有限重试。减少空闲同步心跳作为降低竞争的优化。

范围是面板构建、重建和恢复的独立任务，以及这些任务使用的同一执行入口。导入、追加和同步中与源数据同事务提交的增量聚合保持原子语义，不拆入此队列。它们仍可能与独立构建争用 SQLite 写锁，由锁处理及原有数据集互斥保护。

不新增依赖或数据库结构，不更换 SQLite 驱动，不修改 WAL / FULL、加密密钥、原始行情、回放序号和交易事实。不修改 node_modules，不在 Prisma 已开启事务内嵌套 `BEGIN IMMEDIATE`。

## 2. 全局持久化队列：只安排独立聚合任务

复用 `MarketAggregationJob` 的 QUEUED、RUNNING、COMPLETED、CANCELLED、FAILED、INTERRUPTED 状态、每数据集唯一 `activeDatasetId` 和现有 workerToken / leaseUntil。无需新增全局租约表：SQLite 写事务串行化“检查全局运行状态并认领一个任务”，RUNNING 任务的有效租约作为执行资格。workerToken 按状态解释：QUEUED 保存本次入队轮次的唯一 token，RUNNING 保存认领后的唯一执行 token；终态清空。不能把毫秒级 updatedAt 当作唯一轮次身份。

- API 只持久化入队并触发一次调度，不再为每个点击无条件启动独立构建。每次新建或明确恢复入队，生成新的 queue token，固定于本次请求的事务重试之外并持久化到 workerToken；重复点击返回已有 QUEUED / RUNNING 任务及其原身份，不重复创建代次或更换 token。QUEUED 不持续占用数据集更新租约或 SQLite 写事务。
- 排序使用现有不可变字段 `(createdAt, id)`，按任务最初创建顺序处理。恢复同一任务保留原顺序，不承诺“按此次恢复时间重新排到队尾”。状态查询、心跳和取消不改变排序依据；不使用不断变化的 updatedAt 排队。
- 任意执行入口，包括 worker 脚本、基准脚本及直接调用 `processAggregationJob()`，都必须经过同一个全局原子认领原语。未轮到请求的 job 时，明确返回“未认领/延期”，不静默改为构建另一个任务；调用方和测试必须区分已完成、终态与延期，不能把函数正常返回当作该 job 已完成。进程内变量只减少重复启动，不承担跨进程互斥。
- 认领事务先执行参数化条件 UPDATE 取得 SQLite 写入资格，例如对已选候选任务做 `SET status = status WHERE id = ? AND status = 'QUEUED'`，必须验证它确为首条业务 SQL 且实际取得写入资格。取得资格后取新时间，重新检查全部 RUNNING 任务的 job 与数据集成对租约，回收已失效执行，再重新选择最早可执行 QUEUED。存在有效 RUNNING 时退出，不认领第二个任务。
- 候选任务和租约必须在同一事务重新校验；认领使用 jobId / QUEUED / 选中时的 queue token CAS，数据集更新租约获取与 QUEUED → RUNNING / 新执行 token / leaseUntil 更新原子提交。固定本次认领的 owner/执行 token，提交结果不明先按该身份核对。候选已被取消、重新入队或认领时，不越过检查强行执行。
- 队首任务遇到明确源版本变化等确定性问题，记录 FAILED 并释放其活动标记；遇到仍有效的数据集更新租约时保留 QUEUED，调度本轮跳过它，允许后面的可执行任务运行。只对符合条件的任务维持上述顺序，不能让一个暂不可执行任务永久堵塞其他数据集。
- 独立聚合调度 runtime 由 Node 服务初始化，与 `MARKET_DATA_SYNC_ENABLED` 解耦。启动即扫描，入队和任务结束后唤醒，兜底每 5 秒只读轮询。重复 runtime、重复唤醒或重复子进程仍由数据库认领保证只有一个有效执行者。
- 只读探测发现有效 RUNNING 时，不因其他 QUEUED 重复 spawn；发现过期或异常 RUNNING 时触发显式受保护回收，即使没有任何 QUEUED 也要恢复正确的中断状态。探测结果只决定是否尝试，最终判断仍在写事务内完成。
- runtime 只读探测后启动候选子进程，传入 jobId 与选中的 queue token，由子进程原子认领；直接执行入口也先捕获并绑定该入队身份。本地在途标记与失败退避减少重复 spawn。spawn 失败或子进程在认领前退出时保持 QUEUED，记录诊断并由后续轮询重试，不将已认领或后来恢复的任务误标 FAILED。延迟启动的旧子进程不能认领同一 job 的新入队轮次。
- 浏览器关闭不影响队列。服务重启后，QUEUED 自动继续调度；失联 RUNNING 到期后转 INTERRUPTED、保留检查点并让后续队列继续，原失联任务等待用户手动恢复。不自动重试 FAILED 或 INTERRUPTED 任务。

全局执行资格只防止两个构建同时有效运行，不是持有整个构建时长的 SQLite 写锁。进程在租约到期后仍可能存活，但旧 worker 必须在下一次写入前发现资格失效并停止。

## 3. 排队、取消和所有权的完整规则

现有 `activeAggregationJob()` 会将等待超过 120 秒的 QUEUED 判为 INTERRUPTED，必须删除该规则。正常 QUEUED 可等待任意时长；执行租约超时只适用于 RUNNING。RUNNING 缺少有效 worker 身份或 job 租约等异常状态，也应在有保护的回收事务中处理，不能成为永久阻塞项。

拆分纯状态查询和过期回收。调度只读探测、GET 状态和队列查询不得隐式写数据库。显式回收先取得写入资格，再使用新时间、原 jobId/status/token/updatedAt、job 租约及数据集租约核对；CAS 失败重新读取，不能中断已续期或已接管任务。只清理匹配旧 owner 且确实失效的数据集租约，不能释放其他业务或新 worker 的租约。事务内调用使用同一 tx 原语，由外层重试，不嵌套事务。

QUEUED 可以直接取消并释放 activeDatasetId，不启动 worker；RUNNING 设置取消标记，最多完成当前原子批次，下一批前退出。取消绑定请求开始时的 jobId、status 和 workerToken：QUEUED 使用该轮 queue token，RUNNING 使用该轮执行 token，updatedAt 只作为辅助条件。取消重试不能误取消随后恢复、认领或新建的任务；即使同一毫秒内取消再恢复、updatedAt 相同，新的 queue token 也使旧取消 CAS 失败。认领与取消的先后竞争必须有明确冲突结果。

创建时 jobId / generationId、认领时 owner/token 在重试回调外固定。恢复保留原 job / generation / 已提交游标，验证规则版本、historyVersion、fingerprint 和 targetSequence；不把源已变化的旧检查点当作可恢复状态。终态、旧执行和未知提交结果都不能被后到错误处理覆盖。

排队期间保留原有同数据集源数据更新互斥：追加、同步或元数据更正应返回明确忙碌或按既有规则等待，不让排队时的目标历史悄悄变化。这不限制绘图、交易、复盘等会话操作；不得把数据集更新互斥扩大为所有前台功能禁用。

## 4. 短批次、写入资格与锁重试

聚合每批最多 4096 根，保留现有内存与读取预算，不跨整个任务持有事务。每批及最终发布的首条业务 SQL 是不延长期限的 owner 条件写入，如 `UPDATE MarketDatasetUpdateLease SET owner = owner WHERE datasetId = ? AND owner = ?`。用真实连接与 SQL 跟踪证明写锁语义；不能依赖可能预读的 ORM 调用顺序。

写入资格取得后才获取新时间，重新检查 job 为 RUNNING、workerToken/owner 匹配、job.leaseUntil 与 datasetLease.expiresAt 均有效、取消状态、源版本、fingerprint、targetSequence 及 job/generation 游标一致。第一条写入不能顺便续租，避免锁等待后把过期执行复活。校验失败回滚并停止旧 worker；校验通过后，同事务成对续租、写摘要和检查点。批次开始和提交前检查剩余租约安全余量，不能发布已失去资格的结果。

最终发布仍将旧代次退休、新代次 READY、activeAggregationId 和任务 COMPLETED 原子提交；失败或取消保留已有活动代次。心跳非重入，成对检查并续期两份租约，过期但未被接管的旧 worker 同样不能复活。结束前停止新心跳并等待在途心跳退出。清理只作用于自身 owner/token。

服务端提供显式数据库重试工具，只重试确认已回滚的结构化 SQLITE_BUSY / SQLITE_BUSY_SNAPSHOT 等白名单锁错误；通过真实适配器探针确定当前 native 和 better-sqlite3 的错误映射。不按错误文案模糊匹配，不将所有 Prisma 超时、唯一约束、磁盘/权限错误视为瞬时冲突。

每次重试结束旧事务、释放快照、退避，然后重新运行完整数据库事务，不能只重试 createMany。后台每个原子操作最多 8 次尝试、累计执行/等待目标预算 30 秒，50ms 指数退避至 1000ms 并加抖动，剩余预算不足时不启动新尝试。底层同步 busy timeout 无法由 JS 计时器硬中断，必须测量单次超出目标预算的边界，不承诺硬性 30 秒内返回。

覆盖入队、恢复、全局认领、批次、发布、心跳、取消、过期回收、终态和租约释放。仅可在原子状态转换确认成功后启动后续步骤。若 COMMIT 结果不确定，停止该 worker 后续批次和心跳，按固定身份及持久化检查点进行有界核对；无法判明时记录并等待租约恢复，不能盲目重放或将可能 COMPLETED 的任务改成 FAILED。

后台锁重试耗尽时，在仍有有效所有权的前提下标 INTERRUPTED、保留最后已提交检查点，让调度器处理后续任务。若连终态写入也受阻，只记录并由租约到期回收，不伪报状态保存成功。确定性错误为 FAILED。旧代次摘要回收也使用短事务、有限锁重试和事务外让步，避免任务 COMPLETED 后的清理成为未受控写入；保留至少 24 小时和原有数据保护边界。

## 5. 前台操作继续执行的具体边界

| 操作或场景 | 处理方式 |
| --- | --- |
| 保存绘图、复盘内容、交易日志，普通 AI 文字对话 | 不进入聚合队列；相关数据库原子写入处理短暂锁冲突 |
| 使用其他已就绪数据集回放，或当前数据集按源周期回放 | 不等待整个构建；保留既有会话、纠错和进度限制 |
| 同数据集首次构建，读取高于源周期的窗口 | 仍返回现有 AGGREGATION_NOT_READY，等待聚合就绪 |
| 重建时仍存在符合当前版本和指纹的旧活动代次 | 继续读取旧代次，成功后原子切换 |
| AI / PDF 需要尚未就绪的高周期图表 | 对应图表能力等待就绪，普通文本保存和对话不因此全局阻塞 |

必须审计并覆盖回放推进、下单/撤单、绘图、复盘、交易日志和 AI 记录的数据库写入入口。仅给后台加重试不能声称上述前台已经受保护：前台也可能先读后写，被后台提交使快照失效。

前台仅重试已确认回滚的完整数据库事务，沿用会话/projection/historyVersion 校验和完整原子推进，不能拆分账户、订单、成交和进度。事务外预读若影响业务决策，应移入事务或通过版本 CAS 重新验证。每次重试重新读状态，固定同一业务操作的身份；不能将一次用户“下一根”解释为重试后再推进一根，也不能重复成交、保存或创建消息。

不自动重放 HTTP 请求，不把整个 API handler 放入重试。AI 外部请求、计费、流式输出、文件操作及其他外部副作用放在重试回调之外；AI 请求结果只重试本地记录提交。提交结果不确定必须按已有/固定操作身份核对；不能安全核对的入口先补齐相应幂等边界，再开启自动重试。

前台采用单独的较短重试预算，实施前以真实 SQLite busy timeout 探针定参数并记录实际最坏延迟。预算耗尽返回可识别的暂时忙碌结果、保留已有状态；编辑界面须保留未保存内容，并沿既有提示模式提供重试，不伪报保存成功。如果现有页面不能保留输入，应将最小必要修复纳入实现，并先完整阅读 [UI 规范](../ui/ui-guidelines.md)，检查普通 HTTP、键盘、焦点和错误反馈。

聚合批次提交后在事务外主动让步，初始 10–30ms，冲突时指数退避；按实测降低批量大小或增加让步。SQLite 不保证 FIFO 或严格前台优先，不能承诺零等待。混合负载必须同时验证交互尾延迟和后台持续推进；不达标应调整批量/节流后重测，不能仅延长超时。构建等待资格、排队和退避期间都不持有写事务。

## 6. 减少无效同步写入

行情同步 runtime 先纯读取是否有到期配置、待处理任务或本进程仍在执行的同步。空闲时跳过全局同步租约写入；在途任务继续选主和续租。真正执行前仍重新竞争全局同步租约。新任务最迟由下一次原有 15 秒轮询发现，不依赖永久关闭同步消除竞争。

独立聚合队列的轮询不写“空转心跳”，也不借用同步调度租约或受到同步开关控制。两类 runtime 的作用与进程内状态分别维护，避免停止同步时让聚合队列失去调度。

## 7. 实施与验收

建议修改范围：聚合 jobs / worker / 新增独立调度 runtime、Node instrumentation、aggregation API、数据集租约辅助逻辑、显式数据库重试工具及已审计的前台事务入口、同步 runtime、相关测试和操作文档。现有源行情、撮合与聚合算法保持复用。任何界面修改按 UI 规范执行，文案归入 copy。

先在隔离库建立复现及并发验收，再实现原子认领和 QUEUED 规则，随后实现写前资格、生命周期重试与前台保护，最后优化心跳和调节交互延迟。全部并发验收使用真实 WAL / FULL、独立进程和 IPC 屏障；不靠单进程 mutex、mock 错误或固定 sleep 证明正确。

必须验证：

1. 多数据集同时入队、双服务进程调度、重复子进程与所有直接执行入口竞争，任意时刻至多一个有效 RUNNING；最终聚合与串行基线逐字段一致。队首暂不可执行、确定失败或中断后，其他任务继续。
2. QUEUED 等待超过 120 秒仍有效；关闭页面、服务重启、入队后尚未 spawn、认领前退出、认领后崩溃均可按本方案恢复。同步开关为 0 时聚合照常调度。
3. 取消排队任务、取消运行任务、恢复旧任务、重复点击、延迟取消、延迟启动子进程、延迟过期回收、过期但未接管 worker、过期 worker 仍存活和新 worker 接管，均不会误取消、复活或覆盖新执行。强制同毫秒、相同 updatedAt 的取消 → 恢复 → 旧取消/旧认领到达交错，验证唯一 queue token 阻止旧操作影响新轮次。
4. 用 A 读 / B 提交 / A 写稳定复现旧冲突；新逻辑证明 A 首先获得写入资格，B 等待到 A 提交后成功。A 不 await B 提交，避免测试自身死锁。覆盖首条条件 UPDATE 无匹配行、租约行不存在、等待后身份或有效期变化；回滚释放写锁后才能重试。
5. 在聚合期间真实并发执行回放推进、订单操作、保存绘图、复盘、日志和 AI 本地记录，均无需等待整个聚合完成；通过相反事务交错覆盖前台快照失效，验证进度/交易/消息/保存不重复。失败时输入和已提交状态保留，AI 外部调用次数不随数据库重试增加。
6. 同时检查聚合吞吐、批次持锁时长、前台成功率及 P50/P95/最大延迟。按同库同操作无聚合基线对比，目标是本地保存/推进数据库阶段 P95 不超过 `max(基线 P95 × 2, 500ms)`、单次已测最大值不超过 2 秒，AI 网络时间单独计量；这是目标环境验收门槛而非硬实时保证。真实 busy timeout 若造成超标，先在不降低持久性、不影响其他业务语义的范围调整锁等待/批量/节流，再重测；达不到则报告并修订方案，不宣称前台无影响。
7. 持续外部持锁、重试预算耗尽、最终发布冲突、COMMIT 结果不确定、终态/清理失败，均不丢检查点、不重复摘要、不错误覆盖 COMPLETED。覆盖短预算与底层不可抢占调用的实际延迟。
