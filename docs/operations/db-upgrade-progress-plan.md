# 数据库升级进度显示方案

> 文档状态：设计与计划。适用范围：2026-10-24 旧升级入口的进度与取消方案，已有实施记录；不作为 v1.0 之后新迁移链路的实施授权。
> 当前规范：[升级指南](upgrade.md)。

日期：2026-10-24。研究基线：`ce4402b`。

本文为实施依据；进度显示、只读状态查询、取消安全边界和成功后演练副本清理已落地。实际操作及状态语义以 [升级指南](upgrade.md#进度取消与成功清理) 为准。已经运行的旧版命令继续沿用其原实现，不要求中断或重跑。

实现补充：正式库全部核对成功、所有连接和迁移子进程关闭后，仅逐个清理本次目录内的 `rehearsal.db-wal`、`rehearsal.db-shm`、`rehearsal.db`；`before.db`、配置附件、JSON 和日志保留。升级失败保留演练文件；清理失败保持数据库结果 SUCCESS，另用 cleanup 状态和警告报告，不能要求用户重跑升级。锁或报告收尾失败单独标记 FINALIZATION_FAILED。只读查询仅凭 PID 不宣称任务仍活跃；使用 runId 核对进度归属并明确身份未验证。

## 1. 用户可以获得什么信息

运行命令保持 `corepack pnpm run db:upgrade`。完成路径确认和停写确认后，持续显示：

- 当前阶段及子步骤，明确正在操作备份、副本还是正式库。
- 当前表、已完成表数、已扫描行数；有可靠总数时显示该表的百分比。
- 当前步骤耗时及任务总耗时。
- 最近一次业务进度更新时间；无法获得细粒度进度时，每 10 秒输出一次主进程存活提示。
- 完成或失败后的明确结果、报告路径，以及失败发生在正式写入之前还是之后。

示例中的数值仅用于说明界面，不是当前运行任务的实时状态：

```text
[2/8] 创建一致性数据库备份  63.4%  已耗时 00:42
[3/8] 建立数据基线 · MarketBar · 表 13/49
      已扫描 2,400,000 行 · 首次扫描，总行数尚未统计 · 本步骤 00:31
[4/8] 副本升级后核对原字段 · MarketBar · 表 13/49
      2,400,000 / 5,290,668 行 · 45.4% · 本步骤 00:32
[5/8] 副本重复升级验证 · 数据库完整性检查
      本步骤 00:20 · 总耗时 05:18 · 主进程存活，详细进度暂无更新
[7/8] 正式库升级 · 执行兼容初始化脚本 · 已耗时 00:03
[8/8] 最终核对 · 正式库原字段完整指纹
完成：升级及数据核对成功；总耗时 09:12；报告：...
```

阶段编号表示工作顺序，不能按完成阶段数换算总耗时百分比。首版不提供全流程百分比或完成时间倒计时。

## 2. 当前没有进度的具体原因

入口为 [upgrade-sqlite.mjs](../../scripts/upgrade-sqlite.mjs)：

- `fingerprint()` 在同步迭代器中读取每张表，只有全部完成后才返回。当前成功路径约有 7 轮指纹扫描，包含基线、副本全字段、副本原字段、重复演练、正式库写入前复核、正式结果及正式库原字段。
- `checkIntegrity()` 使用同步 SQLite PRAGMA，执行期间没有行级回调。
- `runCommand()` 使用 `spawnSync()`，子进程输出在退出后才写日志。
- 附件复制和演练库复制使用同步文件操作。
- `report.json` 只区分 `backup / rehearsal / apply / complete`，无法指出正在进行哪一轮扫描。

因此，主线程直接增加 `setInterval()` 无法覆盖同步阻塞期间的提示。需要把任务执行与进度显示分开。

## 3. 执行结构

采用一个主线程负责命令交互、显示和进度文件，一个 Worker 负责原有升级流程。只有一个升级任务执行器，各迁移及核对仍按现有顺序串行完成。

```text
CLI 主线程：参数/确认 → 启动单个 Worker → 接收进度、输出存活提示 → 汇总退出结果
                             |
Worker：原有升级流程 → 同步 SQLite 检查/指纹扫描 → 串行执行迁移子进程
```

数据库连接全部在 Worker 内部创建和关闭，不跨线程传递连接、Statement 或原生句柄。主线程不打开业务数据库来判断进度，也不为显示另外运行 COUNT 或完整性检查。Worker 线程与主线程共享进程 PID，现有维护锁的进程归属可保持一致。

项目锁定的 better-sqlite3 支持在 Worker 中执行数据库查询；可参考其 [v12.8.0 Worker 示例](https://github.com/WiseLibs/better-sqlite3/blob/v12.8.0/docs/threads.md) 和 [Node 24.15 Worker 文档](https://nodejs.org/download/release/v24.15.0/docs/api/worker_threads.html)。这里采用单任务 Worker，不采用示例中的自动重试或线程池。

保持 `upgradeDatabase()` 可独立调用，增加可选进度回调，便于现有测试直接验证业务流程。CLI 入口明确限定在主线程运行，Worker 导入模块时不能再次触发交互入口。

## 4. 阶段和进度来源

| 阶段 | 子步骤 | 可以显示的真实进度 |
| --- | --- | --- |
| 1. 核对环境 | 路径、停写确认、锁、驱动及模式 | 各检查开始/完成、耗时 |
| 2. 检查与备份 | 源库完整性/外键、一致性备份、配置与附件复制 | 备份页数百分比；其他子步骤开始/完成及存活提示 |
| 3. 建立基线 | 备份检查、各表指纹、识别升级路径 | 表编号、已扫描行数；首次扫描不要求行总数 |
| 4. 副本升级 | 执行升级、目标结构/完整性、全字段指纹、原字段保留核对 | 子步骤、当前表、行数；可复用基线计数的核对显示表内百分比 |
| 5. 重复演练 | 再执行升级、核对幂等性 | 同上，明确标注第二次演练，避免误认为进度回退 |
| 6. 写入前复核 | 正式库数据、结构、历史、文件身份、升级代码一致性 | 当前检查、表内扫描进度、耗时 |
| 7. 正式升级 | 执行相同升级入口、核对结构和完整结果 | 明确“正在写入正式库”；执行器状态及后续扫描进度 |
| 8. 最终核对 | 原字段保留、完整性、模式、报告和锁处理 | 当前表/检查；全部成功后才显示最终完成 |

### 数据库备份

使用现有 `db.backup()` 的 `progress({ totalPages, remainingPages })` 回调，按已传输页数计算百分比。零页或暂无有效总数时显示状态，避免 NaN。备份 Promise 成功后显式发出完成事件，不能依赖回调一定收到最后一个 100%。

保持原备份批量大小和一致性机制。进度回调不返回新的页数，不为显示而调整备份吞吐。依据：[better-sqlite3 v12.8.0 backup API](https://github.com/WiseLibs/better-sqlite3/blob/v12.8.0/docs/api.md#backupdestination-options--promise)。

### 数据指纹

- 每张表开始、结束立即发送事件；内部每若干行检查一次时间，最多约每秒发送一次累计行数。
- 不改变查询排序、原字段选择、`safeIntegers()`、逐行 JSON 编码、哈希内容和数据保护断言。
- 首次基线扫描只显示已处理行数，不额外执行全库 COUNT 来准备进度分母。
- 后续核对可以复用已核实基线中的 `count`。新表或无对应计数时继续显示已处理行数。
- 参考行数与实际扫描行数不符时，显示“记录数变化，待核验”；不能把超出分母的进度当作核对成功。该表结束及断言通过后才标记完成。
- 表编号按表数显示，不包装成按工作量计算的总百分比。大行情表与小配置表的耗时差别很大。

### 完整性检查与文件复制

首版保留现有 SQLite PRAGMA 及复制实现。这些步骤显示开始、结束和耗时，主线程持续提供存活提示。不按目标文件大小推算复制进度，因为文件可能提前分配全部空间。

### 迁移子进程

将 `runCommand()` 改为异步 `spawn()`，串行等待退出，并增量写入原日志文件。主流程的迁移函数相应使用 `await`，兼容现有同步测试桩，不能遗漏任何一次演练或正式迁移的等待。

终端只打印受控步骤摘要和迁移名称，不直接把所有子进程输出转发到终端。详细日志仍保留在原目录。无子进程输出时显示“等待子进程完成”和耗时，不虚构迁移百分比。

## 5. 进度事件与查询

增加统一事件结构，建议字段：

```text
version, runId, sequence, state, phaseId, phaseIndex, phaseTotal,
stepId, targetRole, tableName, tableIndex, tableTotal,
completedRows, referenceRows, completedPages, totalPages,
startedAt, stepStartedAt, lastWorkProgressAt, heartbeatAt
```

计数缺失使用 null，不能以 0 表示未知。`targetRole` 区分 source / backup / rehearsal。序号递增；不同扫描用不同 `stepId`，避免行计数重置被解释为进度倒退。

- Worker 发出工作进度事件，CLI 主线程统一渲染。
- 交互终端约每秒最多刷新一次当前行；Windows PowerShell 使用普通字符，避免依赖特殊图形字体。
- 输出被重定向时，使用带时间的普通日志行，不发送光标控制符。
- 阶段切换立即输出；长步骤每 10 秒最多补一行当前状态。
- 备份目录增加 `progress.json`，最多每 5 秒原子更新一次；保留 `report.json` 原有最终结果职责，避免两个写入者竞争同一文件。
- `progress.log` 追加阶段切换及节流后的摘要；不写每行事件、业务字段值、环境变量值或密钥。
- stdout 背压时合并中间进度，保留最新状态，避免积压无限队列。
- 进度渲染或可选进度文件写入失败应告警并降级，不能让显示回调异常打断数据库备份或改变数据断言结果。必要备份及最终报告写入失败仍按原保护流程处理。

提供只读入口：

```powershell
corepack pnpm run db:upgrade --status
```

它从维护锁读取本次任务目录，再读取进度和报告；不要求停写确认，不创建锁，也不打开业务库连接。没有活动锁时明确显示无活动任务；查看历史结果可指定报告目录。遇到旧版任务没有 `progress.json`，降级显示粗阶段、进程状态和文件更新时间，不把进度缺失当成任务失败。

“主进程存活”与“业务进度已推进”分开显示。时间戳刷新不能证明 SQLite 一定在前进；长时间没有工作进度只能提示进一步检查，不能自动超时、重试或清理维护锁。

## 6. 任务生命周期与保护

- 主线程只有在 Worker 成功返回、结果校验及锁处理全部完成后，才输出最终成功。退出码继续区分成功和失败。
- Worker 异常退出或迁移子进程失败时，停止进度刷新，明确最后阶段和是否已进入正式写入，保留现有锁、备份及日志，不自动重跑任务。
- 不增加基于固定分钟数的自动失败、恢复或强制终止。
- Ctrl+C 发出取消请求，阻止开始后续步骤；在同步循环中通过共享取消标志检查，在不可中断的原生步骤中等待安全边界。主线程不能自行退出而让工作线程或子进程失去管理。不能为了停止动画直接调用 `worker.terminate()` 中断数据库写入。
- 强制关闭进程仍按现场保留规则处理，不自动删除锁，不用备份覆盖正式库。
- 前次审查发现的隐式关联表校验、初始化代码变更校验，应独立修复和回归。新的执行入口及相关升级实现也要纳入代码一致性保护，进度显示不代替这两项修复。

## 7. 修改范围

建议保持现有业务入口，仅拆出执行和显示职责：

| 文件 | 责任 |
| --- | --- |
| `scripts/upgrade-sqlite.mjs` | 保留核心升级函数和 CLI 参数；增加事件埋点及串行异步子进程执行 |
| `scripts/upgrade-sqlite-worker.mjs` | 单 Worker 的执行入口、进度转发及取消检查衔接 |
| `scripts/upgrade-sqlite-progress.mjs` | 事件约定、终端渲染、存活提示及进度文件 |
| `scripts/upgrade-sqlite.test.mjs` | 原有数据保护回归及新增事件断言 |
| `scripts/upgrade-sqlite-progress.test.mjs` | Worker 阻塞时的提示、状态查询、失败退出和输出节流 |
| `docs/operations/upgrade.md` | 命令示例、输出含义、状态查询与异常处理 |

不引入运行时依赖。实际数据库迁移 SQL、数据库模型及 UUID 规则沿用现有实现。

## 8. 验收

1. 原有 16 项升级测试及前次两项缺陷的新增回归通过。
2. 在隔离 Worker 中制造受控同步阻塞，确认主线程仍能输出存活提示；提示必须标明详细工作进度未更新。
3. 指纹开始/表切换/结束事件准确；首次扫描无分母，复用基线时分母准确；空表、计数变化、零页备份不出现错误百分比。
4. 节流、重定向、Windows PowerShell 输出可用，阶段结束后不残留动画或定时器；输出不含测试密钥和业务字段值。
5. `--status` 在运行中、成功后、旧版进度缺失、进程异常退出及历史报告场景下只读工作；PID 存活判断须防止 PID 重用造成误判。
6. Worker 失败、子进程失败和取消请求正确传播，仍保留原失败现场，不能提前输出成功。
7. 在相同隔离库上比较启用/禁用进度后的结构、全量原字段指纹、WAL 模式及最终结果，证明显示没有改变升级行为。
8. 用约 1.2 GB 备份副本做一次端到端测试，记录总耗时、CPU 和内存；进度开销目标不超过 5%，以实测为准。超出时优先降低消息和磁盘写入频率，不减少数据核对。

只使用隔离测试库或既有备份的新副本验证，不使用正在执行升级的正式库开展实验。
