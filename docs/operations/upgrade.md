| 实际数据库起点 | 目标 | 使用方式 |
| --- | --- | --- |
| v0.2 | v1.0 | 使用 `v1.0` tag 内的旧脚本和同版本升级指南，完成备份、升级和验收。 |

### 新旧脚本的生命周期

1. v1.0 之后首次发生数据库变更时，实现独立的新升级入口，并将 `db:upgrade` 切换到新入口。新入口可以复用核验过的备份、锁和进度等公共能力，但不调用旧兼容升级链路，不继续为 v0.2 等旧库补转换逻辑。
2. 新入口只接受已核验的 v1.0 基线及其后续状态。低于基线、版本无法识别、结构不符或迁移历史异常时停止并报告原因，不自动切换旧脚本、重置数据库或忽略迁移错误。接续初始化路径所得 v1.0 库的具体识别与版本记录机制，须随新入口实现和验证后写入本文。
3. 验证全新安装、两类 v1.0 基线升级、后续连续升级、重复执行和失败保护，保留停写、备份、副本演练、数据核对及密钥要求。有意转换原数据的迁移须提供具体转换断言，不通过关闭全局数据检查放行。
4. 切换 package 命令、安装脚本、Docker 启动流程、测试及 README 等所有调用方后，从主线移除已无引用的旧入口与专用实现；历史实现由 `v1.0` tag 保存，无需长期改名保留。仍被新安装或其他功能依赖的初始化脚本、公共模块须先替换或拆分，不能一并删去。任何文件移除须逐个明确路径，禁止批量删除。
5. 已发布的 Prisma 迁移 SQL 和校验和继续保留。移除旧升级编排不等于删除历史迁移；迁移历史压缩或重新基线化须另有经过验证的接续方案。

## 1. 先确认目标机器的现状

升级前记录以下信息，形成升级清单：

- 当前代码提交、分支、上游和未提交改动；保留本机改动，不用强制重置或清理工作区获取更新。
- 部署方式：本地 Node 的 `start`、开发服务、Docker 开发 Compose 或 Docker 生产 Compose。
- 当前 `SQLITE_DRIVER`、`SQLITE_JOURNAL_MODE`、应用实际 SQLite 版本与日志模式，以及 Node 版本、操作系统/架构、镜像摘要；系统 `sqlite3 --version` 不能代表应用引擎。
- 真正使用的 `DATABASE_URL` 与数据库绝对路径。默认 Node 配置 `file:./dev.db` 指向 `prisma/dev.db`；生产 Compose 为容器 `/data/dev.db`，来自 `app_data` 命名卷。不要把宿主机同名空库误当成生产库。
- 数据库是否由 Prisma 迁移管理：检查 `_prisma_migrations`、已完成/失败的迁移和实际表结构。旧的 `db:init-sqlite` 不维护 Prisma 迁移历史，不能仅凭表存在就认为迁移状态正常。
- `.env` / 服务环境变量、行情同步加密主密钥、`storage/` 截图、导入任务文件以及 Docker 卷的实际位置。
- 是否还有行情导入、行情同步或回退重建任务；先让任务结束，或按现有流程取消，避免升级跨越未完成写入。

只升级这台机器的现有数据库，保留该机器的数据。不要将开发机的 `dev.db`、`.env`、密钥或 `.next` 覆盖过去。

## 3. 获取代码并选择迁移路径

> 本节的旧数据库迁移命令仅用于升级到 v1.0，须在 v1.0 tag 的完整代码与依赖环境中执行。以下原初始化 / Prisma 双路径不是 v1.0 之后的新升级入口；后续数据库变更须按顶部基线规则提供并验证新入口。

拉取已确认的目标分支或提交；使用快进更新，遇到本地改动或分叉先保留并处理。记录最终提交；有多个后续提交时无需按功能逐次启动应用，但必须执行目标代码全部尚未应用的数据库迁移。

本地 Node 部署沿用目标机器现有的兼容版本，不固定 Node 主版本，也不要求与 Docker 基础镜像一致。Dockerfile 中的 Node 22 是容器构建的参考环境，不作为其他机器的版本限制。升级时记录实际 Node 版本，并在该版本下完成依赖安装、测试、生产构建和启动验收；确认所用版本支持项目测试使用的 `node:sqlite`。安装依赖并生成 Prisma Client：

```powershell
node --version
corepack pnpm install --frozen-lockfile
corepack pnpm run db:prepare-sqlite
corepack pnpm prisma generate
```

每条命令成功后再执行下一条。`db:prepare-sqlite` 只探测内存数据库及准备原生模块，不会切换业务库；启用新驱动前必须成功输出 SQLite `3.51.3`。若安装使用了 `--ignore-scripts`，不能省略这一步。缺少目标平台/Node ABI 的预编译文件时先解决安装或构建环境，不复制其他操作系统的 `node_modules`。仅沿用 native 时该准备命令可跳过。

若 Windows 环境无法解析 Prisma 命令，可使用项目中的 `node node_modules/prisma/build/index.js ...` 执行相同 Prisma 子命令。

**已有 WAL 库保持原日志模式离线升级。** Prisma CLI 不经过应用的 `lib/sqlite-client.mjs`，设置 `SQLITE_DRIVER` 不会替换它的迁移引擎；初始化脚本则复用应用连接工厂，可明确使用已验证的新驱动。两条升级路径都不要求先转 DELETE，具体顺序见 [已有 WAL 库的迁移顺序](#已有-wal-库的迁移顺序)。CLI 只在所有应用及 worker 停写、完成备份副本验证的离线阶段使用，不据此放开旧 native 应用驱动访问 WAL 的保护。Prisma CLI 的配置与应用 Client 独立，见 [Prisma v6 配置说明](https://www.prisma.io/docs/orm/v6/reference/prisma-config-reference)。

### 旧升级入口（仅用于升级到 v1.0）：离线升级编排

> 旧入口：`scripts/upgrade-sqlite.mjs`。仅用于目标为 v1.0 的旧库升级，不代表后续升级入口已经实现。

在 v1.0 tag 环境安装依赖并生成相应 Prisma Client 后，可以使用该版本的编排入口；它复用原迁移 SQL 或 `init-sqlite.mjs`，不另建迁移实现，也不自动构建或启动服务：

```powershell
corepack pnpm run db:upgrade
```

命令读取项目 `.env`，已有进程环境变量优先，按应用相同规则解析 `DATABASE_URL`（相对路径基于 `prisma/`）。交互模式要求输入实际数据库绝对路径，并确认本项目服务、同步、导入及所有 worker 已停写；命令不会自动停止进程。非交互部署需明确提供核对路径及停写声明，例如：

```powershell
corepack pnpm run db:upgrade --expect-database "D:/实际部署目录/prisma/dev.db" --stopped --backup-dir "D:/数据库升级备份"
```

该示例路径须替换为目标机器的实际路径。不存在的数据库、路径不匹配或未确认停写均直接拒绝，不代建空库。维护驱动使用项目锁定的 better-sqlite3，需先完成 `db:prepare-sqlite`；应用仍可沿用 native。

流程如下：

1. 独占创建 `<数据库路径>.upgrade.lock`，防止升级命令相互并发。它不是应用维护锁，不能代替实际停止服务和 worker。
2. 核对完整性与外键，通过 SQLite backup API 创建包含已提交 WAL 页的一致性 `before.db`；保存逐表全量 SHA-256、行数和原字段基线，不采样。同步复制存在的 `.env`、`storage/`、`.market-imports/`，不改原环境或密钥。服务环境及 Docker 卷挂载不在这些路径内的文件仍须按第 2 节另备份。
3. 识别原安装方式：没有迁移历史表的可识别业务库走原初始化脚本；有完整、校验和匹配的迁移前缀走 `prisma migrate deploy`。空历史、未完成/失败记录、分叉或校验和不符均停止，不自动换路径、重置或标记迁移完成。允许 LF/CRLF 换行差异，不允许 SQL 内容变化。
4. 在独立 `rehearsal.db` 上执行原升级入口，关闭行情同步；再执行一次验证幂等性。检查目标模型表/字段，以及 Prisma 未列为独立模型的隐式多对多关联表和 A/B 字段（包括 `_TradeToTradeTag`、`_ReplayJournalTradeReasons`）；检查完整性、外键、原字段全量数据及重复执行结果。迁移历史完整不能代替实际结构校验；缺表时 Prisma 路径停止，不自动改用初始化脚本。
5. 复核正式库自备份后未变化、数据库文件未被替换、迁移文件及 schema 未变化。演练前记录升级入口、Worker、进度显示入口、初始化脚本及所选 CLI 入口、本地 SQLite 连接工厂、生成的 Prisma Client、package.json 和锁文件的 SHA-256；每次子进程执行前后以及正式升级前复核，缺失或变化时停止后续阶段，不等到正式数据被修改后才判断结果。执行期间不得并行拉取代码、安装依赖或修改脚本。通过后对正式库执行同一路径。正式结果的表结构与全量数据须与演练一致，原字段数据还需与备份一致。
6. 两条路径都保持源库原先的 WAL/DELETE 模式，不强制 checkpoint 或临时转 DELETE。演练副本在必要时设为源库模式，正式库模式若被外部改变则拒绝升级。初始化子进程使用 better-sqlite3；CLI 仍使用其自身引擎，不能视为继承了新适配器。写锁冲突直接停止，不删除 WAL/SHM。子进程维护连接临时使用 FULL，不改原 FULL/NORMAL 配置，应用重启后仍按原配置连接。
7. 正式升级及全部核对成功、所有数据库连接和迁移子进程关闭后，逐个清理本次目录中的 `rehearsal.db-wal`、`rehearsal.db-shm`、`rehearsal.db`。不跟随链接，不扫描清理其他文件，保留 `before.db`、配置附件、摘要和日志。成功写出报告并释放维护锁；重复运行仍建立新的备份和演练目录，不覆盖上次现场。默认备份根位于项目检出目录的同级 `<项目目录名>-db-upgrades/`，也可用 `--backup-dir` 指定。

每次目录保留 `before.db`、`baseline.json`、演练/正式数据摘要、各子进程日志、`progress.json`、`progress.log` 和 `report.json`；升级失败时还保留 `rehearsal.db` 及其 WAL/SHM。报告包含路径、选择的迁移方式、原日志模式、实现代码校验和（implementationChecksums）、所选执行代码清单及摘要（executionCode）和迁移校验和、失败阶段或成功结果。备份含私有数据和可能的密钥，应限制目录访问，禁止加入 Git 或 Docker 构建上下文。

#### 进度、取消与成功清理

命令确认后由单个 Worker 串行执行升级，主线程持续显示八个阶段：核对环境、检查与备份、建立基线、副本升级、重复演练、写入前复核、正式升级、最终核对。备份显示实际页进度；指纹显示当前表、表编号、已扫描行数和可核实的参考行数。首次扫描没有总行数，不为显示额外执行全库 COUNT。表内记录数变化会显示“待核验”。阶段编号不能当作全流程百分比，没有预计完成倒计时。

同步完整性检查、复制和等待迁移子进程期间，主线程每 10 秒输出“主进程存活，详细工作进度暂无更新”及耗时。这只能证明显示主线程仍运行，不能证明数据库查询持续推进。`progress.json` 保存最新业务进度、业务时间和显示心跳；阶段/表切换立即写入，行数变化及心跳通常最多每 5 秒写一次。`progress.log` 只保留步骤和节流摘要，不记录业务字段值和密钥。进度显示或可选进度文件故障降级警告，不能绕过数据检查；必要备份和最终报告写入失败仍停止。

可在第二个终端只读查询，不需要重新确认停写，也不打开业务数据库或获取新锁：

```powershell
corepack pnpm run db:upgrade --status
corepack pnpm run db:upgrade --status --report-dir "D:/实际备份目录/本次任务目录"
```

无活动锁时显示 `NO_ACTIVE_TASK`，历史报告须指定目录。旧任务没有进度文件时显示报告粗阶段；PID 已退出显示 `PROCESS_NOT_FOUND`。仅有存活 PID 不代表原任务存活（PID 可能复用），显示 `IDENTITY_UNVERIFIED`，并核对 `runId` 后才显示该锁对应的进度。只读历史目录尚为 RUNNING 时标记 `RUNNING_UNVERIFIED`，不会认定已完成或自行清锁。

按 `Ctrl+C` 请求取消；命令会等待同步原生调用或正在运行的迁移子进程结束，在扫描检查点或下一步骤边界停止，不强制终止 Worker。迁移子进程单独使用进程组/隐藏控制台，仍受父任务等待管理，避免 Ctrl+C 广播直接打断写入。取消后保留演练副本和维护锁。若报告 `formalWriteStarted: true`，正式写入阶段已开始，必须检查实际数据库状态；不要直接重新运行。全部正式核对成功后的清理和报告收尾不再受取消影响。强制关闭窗口仍可能留下现场，不能等同于安全取消。

数据库及核对成功时 `report.status` 和 `databaseStatus` 为 `SUCCESS`，`cleanup.status` 单独为 `COMPLETE`、`PARTIAL` 或 `FAILED`，列出已删除、原本不存在、剩余文件及错误。演练文件被占用或路径异常时，升级仍报告成功并警告“清理未完成，无需重跑升级”，保留剩余文件供人工处理。最终报告或锁释放失败则为 `FINALIZATION_FAILED`，保留 `databaseStatus: SUCCESS`，同样不应重跑数据库升级。CLI 只有在 Worker 返回结果并退出后才打印最终成功。

CLI 界面是 UI 规范的范围例外：规范以桌面浏览器为主，原生 Node ESM 维护命令无法直接加载 TypeScript 的 `lib/i18n.ts` / `lib/format.ts`，因此新增进度文案及数字格式集中于 `scripts/upgrade-sqlite-progress.mjs`，使用简体中文和普通字符日志；验证覆盖格式、重定向、背压、同步阻塞心跳、状态只读及取消生命周期，不改动网页组件。

**保守的数据保护限制：** 统一入口只自动放行不改变原有行与字段的升级，可添加表和列。旧版本升级涉及物理 ID 转换、旧结果清理、历史字段回填或删除旧派生摘要时，原脚本即使正常执行，也可能在演练的原数据核对处停止；这是保护门，不提供忽略校验的强制开关。应保留演练报告，按本文旧迁移说明确认具体转换，再采用经过单独核验的原路径处理，不能因失败直接改走另一迁移方式。

**失败处理：** 正式库可能尚未修改，也可能停在部分升级状态，以报告阶段和实际结构为准；编排不为升级切换正式库日志模式。命令保留数据库、WAL/SHM、备份、副本、日志及 `.upgrade.lock`，不会用备份自动覆盖。保留现场并查明失败原因，确认原进程已退出、无其他升级任务后，才按明确路径单独移除该锁，再按已核实状态重新运行；不要批量清理或直接重启仍不兼容的旧服务。仅保留锁不代表仍有进程正在运行。

### 路径 A：Prisma 迁移历史完整（手动流程）

> 旧手动路径，仅用于升级到 v1.0。不能用此节绕过后续版本的新入口校验。

先将备份复制为隔离演练库，在独立进程中让 `DATABASE_URL` 指向副本，再检查和应用迁移；不要为了演练改写生产 `.env`。迁移后的应用试运行设置 `MARKET_DATA_SYNC_ENABLED=0`，防止副本自动调用行情提供商。

```powershell
corepack pnpm prisma migrate status
corepack pnpm prisma migrate deploy
corepack pnpm prisma migrate status
```

升级前 `status` 报告待应用迁移是预期情况；读取具体原因，区分待迁移与连接错误、失败迁移、历史分叉。演练通过后，对仍停止写入的正式库执行相同迁移。

生产升级使用 `migrate deploy`。不要使用 `migrate dev` 生成新迁移，不使用 `migrate reset`、删除数据库、`db push --accept-data-loss` 或跳过 SQL 的方式消除错误。

### 路径 B：旧数据库使用 SQLite 初始化兜底，迁移历史缺失或不一致

> 旧兼容路径，仅用于升级到 v1.0。后续新入口须单独核验无迁移历史的有效 v1.0 基线库，不能继续调用此脚本兜底。

此时直接执行 `migrate deploy` 可能出现 P3005、表已存在或重复列错误。先对照实际结构和数据转换状态，确定原安装使用的方式；不要把全部迁移直接标记为已执行，也不要在失败迁移之后盲目运行初始化脚本。

仓库保留兼容升级入口：

```powershell
corepack pnpm run db:init-sqlite
```

该脚本会修改已有数据库，包含多会话转换、单份结果清理及关卡字段补齐，不是一个只创建空表的命令。只有确认适用于目标旧库、在备份副本演练并核对数据后，才对正式库使用。

使用兜底脚本不会补齐 `_prisma_migrations`。若随后切换到自动执行 `migrate deploy` 的 Docker 生产方式，需先在副本上验证并建立与真实状态一致的迁移基线；Prisma `migrate resolve` 只能用于已经核实完成的迁移，不能代替数据转换。无法确定状态时停止正式库写入，保留现场并说明具体差异。

### SQLite 引擎与 WAL 升级

#### 版本与配置来源

| 项目 | 当前代码中的位置与要求 |
| --- | --- |
| Prisma Client / CLI / 适配器 | [package.json](../../package.json) 与 [pnpm-lock.yaml](../../pnpm-lock.yaml)，均锁定 `6.19.3` |
| 新驱动 | `better-sqlite3` 锁定 `12.8.0`，内置 SQLite `3.51.3` |
| 适配器传递依赖 | [pnpm-workspace.yaml](../../pnpm-workspace.yaml) 定向覆盖为同一驱动版本 |
| 运行时校验 | [连接工厂](../../lib/sqlite-client.mjs) 对新驱动每条实际连接要求 `3.51.3`、外键开启、同步级别与配置一致（默认 FULL=2；显式 WAL + NORMAL=1），日期保留 Unix 毫秒 |
| 默认安装 | [环境示例](../../.env.example) 为 `SQLITE_DRIVER=native`、`SQLITE_JOURNAL_MODE=delete`；native 引擎版本取决于 Prisma 内置引擎，本机实测为 `3.46.0` |

适配器 `6.19.3` 上游声明的驱动范围是 `^11.9.0`，本项目的 `12.8.0` 覆盖超出该范围。这组锁定组合已在 Windows / Node 24.15.0 验证；Linux、其他 Node 版本与生产镜像需在目标环境完成验收。不要单独升级 Prisma、驱动或锁文件后沿用旧结论；连接工厂会拒绝未经校验的 SQLite 版本。版本依据、测试范围及剩余事项见 [SQLite 验证记录](sqlite-wal-validation.md)。

更新操作系统的 SQLite 工具不会更换应用引擎；仅拉取代码也不会自动启用 WAL。同步级别默认 FULL；可按下文配置为 NORMAL，连接工厂会核对每条连接的实际值。

#### 同步级别

默认 `SQLITE_SYNCHRONOUS="FULL"`。若接受断电或系统崩溃后最近已提交事务可能丢失，可在已有 better-sqlite3 + WAL 安装中设置：

```dotenv
SQLITE_DRIVER="better-sqlite3"
SQLITE_JOURNAL_MODE="wal"
SQLITE_SYNCHRONOUS="NORMAL"
```

NORMAL 仅支持上述驱动与日志模式组合，不提供 OFF 配置。按第 2 节完成备份，再更新配置、构建并重启本项目服务和 worker，核对运行日志为 `wal / synchronous:1 / synchronousMode:NORMAL`。旧版本将 FULL 写死，仅加环境变量不会生效；容器必须显式传入该变量。

恢复 FULL 时将 `SQLITE_SYNCHRONOUS` 改回 `FULL` 并重启所有相关进程，核对 `wal / synchronous:2 / synchronousMode:FULL`。只改变同步级别无需迁移表结构或恢复旧数据库，保留现有 WAL/SHM。

#### 副本演练与正式切换

1. 完成第 2 节备份，并将一致性备份另复制为可写演练库，保留原始备份。核对路径和记录基线；新驱动遇到不存在的库会直接拒绝启动，不会代建空库。
2. 在目标 Node/平台下完成依赖安装与 `db:prepare-sqlite`，先按第 3 节适用路径完成演练库的结构迁移。
3. 在**单独的演练终端**设置副本绝对路径与新驱动。以下路径仅为示例，必须替换为实际已存在的副本；正式服务保持停止，不改生产 `.env`：

   ~~~powershell
   $env:DATABASE_URL = "file:D:/upgrade-check/working.db"
   $env:MARKET_DATA_SYNC_ENABLED = "0"
   $env:SQLITE_DRIVER = "better-sqlite3"
   $env:SQLITE_JOURNAL_MODE = "wal"
   corepack pnpm run db:runtime --integrity
   ~~~

   Linux 路径使用 `file:/绝对路径/working.db`。相对 `file:./dev.db` 仍指项目的 `prisma/dev.db`，不要误解为当前目录同名文件。

4. 核对诊断中的数据库绝对路径、driver=`better-sqlite3`、version=`3.51.3`、journalMode=`wal`、synchronous=`2`、foreignKeys=`1`、integrity=`ok`，且 foreignKeyCheck 为空。继续在此副本完成测试、构建及隔离会话验收；独立 worker 也须使用同一驱动配置。
5. 演练通过后，关闭演练进程。对仍停止写入的正式实例，完成必要迁移，再在**原正式配置**中增加下列两项，保留原 `DATABASE_URL`、密钥与文件路径：

   ~~~dotenv
   SQLITE_DRIVER="better-sqlite3"
   SQLITE_JOURNAL_MODE="wal"
   ~~~

6. 正式连接前再次确认备份和目标路径，以正式环境执行 `corepack pnpm run db:runtime --integrity`，核对同一组结果，再启动新服务并按第 6 节验收。服务环境变量优先于 `.env`；不要让正式启动继承演练库的 `DATABASE_URL` 或临时覆盖。

**`db:runtime` 会打开应用连接并应用配置的日志模式，它不是纯只读诊断。** 在正式库运行前必须停止服务/worker、备份并确认路径；切换模式失败时保留现场，不删除 `-wal` / `-shm`。实际页面/API 建立连接后，服务器 `sqlite-runtime` 日志应再次显示 `3.51.3 / wal / synchronous:2`；只检查安装输出或环境变量不足以证明生效。若已明确选用 NORMAL，同步级别应为 `1 / NORMAL`，并确保应用和 worker 都继承同一配置。

提交延迟可用 `corepack pnpm run diagnose:sqlite-commit --samples 160` 作隔离诊断：工具只在 `tmp/sqlite-commit-diagnostics/` 新建合成库和文件，不读取业务数据库；对比直接 COMMIT、Prisma、检查点和文件同步，最后输出报告路径。NORMAL 对照仅作用于合成库，不能将其结果直接视为生产环境收益。

#### 已有 WAL 库的迁移顺序

> 本节初始化 / Prisma 双路径仍限于升级到 v1.0；保持原日志模式、停写、备份和核验原则继续适用，后续版本采用其适用的新入口。

已经启用 WAL 的安装，后续结构升级保持 WAL，不临时转 DELETE。此前文档要求一律切换是针对旧迁移引擎的保守策略，不是 SQLite 修改结构的必要条件；现以本节替代。

1. 停止本项目服务及全部 worker，确认没有导入、同步、纠错或其他写入，保留实际数据库路径、新驱动和原 FULL/NORMAL 配置。
2. 优先运行 `db:upgrade`，通过 SQLite backup API 获取包含已提交 WAL 页的一致性备份。在副本保持 WAL，按识别结果执行初始化或 `migrate deploy`，复跑验证，再升级正式库。
3. 初始化路径使用 better-sqlite3 / SQLite 3.51.3；CLI 使用其独立引擎。即使 CLI 可以离线处理 WAL，也不能因此将应用改回 native，或允许 CLI 与业务服务并发写入。
4. 核对升级后仍为 WAL、完整性/外键和原有数据正常；关闭迁移进程后再构建、启动和验收。目标 Linux/容器环境仍须先完成同样副本验证，本机结果不能代替目标平台验收。

不手工删除 WAL/SHM，不要求为了本次升级强制 checkpoint。若仅部署无结构变更的性能代码，不必为提速运行初始化脚本。只有明确回退为旧 native 应用驱动时，才按回退章节单独转换日志模式。

## 5. 配置与生产构建

### 行情同步

- 保留已有 `MARKET_DATA_ENCRYPTION_KEY` 原值；它用于解密数据库中的 Databento API Key，不能每次升级重新生成。不在日志、报告或对话中输出密钥。
- 从未配置行情连接的新安装，按 [行情同步说明](../market-data/market-data-sync.md) 创建一次密钥并持久保存。
- 副本演练与首次升级验收先设置 `MARKET_DATA_SYNC_ENABLED=0`；正式验收后再恢复原设置。不要为测试主动执行付费下载。
- 本地 Node 部署需要在服务运行环境中传入配置；生产 Compose 已映射这两个变量。拉取代码不会自动复制另一台机器的环境变量。

### AI 配置

AI 使用独立的 `AI_ENCRYPTION_KEY`，保留原行情主密钥不变。本地可运行 `node scripts/setup-ai-key.mjs` 生成一次并保存在 `.env`，随后重启服务；已有有效配置不覆盖。备份更新后的环境配置、数据库及 `storage/ai/`，普通业务导出不包含密钥。详见 [AI 机器人说明](../ai/ai-assistant.md)。

AI 普通聊天在窗口内运行，会话分析依赖独立 worker。升级前停止或等待这些活动任务；中断任务需要用户显式继续，不能自动重复未知计费状态的步骤。

### 本地 Node 的 start 模式

直接使用已完成兼容验证的 Node，不依赖本机临时备份中的运行时。开发模式运行 `corepack pnpm dev`；生产模式先在关闭行情同步、指向演练副本的终端完成检查与构建：

```powershell
corepack pnpm lint
corepack pnpm test
corepack pnpm run build
```

结束演练进程。在正式服务管理器或另一个终端中恢复原正式数据库、密钥和行情同步设置，完成正式库迁移及运行时核对，再启动服务；不能沿用演练库的环境覆盖：

```powershell
corepack pnpm start
```

新代码必须重新构建，重启旧 `.next` 不会获得全部改动；重启后刷新已打开的回放页面。从开发模式切换到生产模式时，先停止开发服务，再重新构建并运行 `start`。测试和构建不要与操作正式库的服务并发；Windows 下 Prisma DLL 占用时确认并停止本项目相关进程后重试。隔离库试运行必须使用另一端口和数据库，避免覆盖或混用正式实例。

### Docker 部署的额外检查

仓库的两个 Compose 文件用途不同：

- `compose.yaml` 挂载源码并启动 `dev`，不是生产 start 部署。
- `compose.prod.yaml` 当前引用 `sudongpojiaozi/monte-carlo-simulation-report:v0.1`，没有 `build` 配置；仅拉取仓库代码或执行 Compose 的 `up --build` 不会从最新源码生成该生产镜像。应构建并发布/指定包含目标提交的镜像，记录摘要，保留原数据卷。
- `Dockerfile.prod` 默认启动命令每次都会先执行 `prisma migrate deploy`。创建新容器前必须完成备份和迁移路径检查；迁移保持原模式并单独离线完成后，WAL 服务仍须覆盖启动命令为仅启动 Next，避免普通重启未经备份和演练就执行迁移。旧初始化方式的库也不能未经迁移基线处理就使用默认启动命令。
- AI 版本的生产 runner 已补充 `scripts/`、`lib/`、`tsconfig.json`，供回退与 AI 分析 worker 运行。仍需发布包含当前代码的镜像，并实测子进程、环境变量与持久化；仅首页 healthcheck 成功不能证明 worker 可用，本次未发布或实机验证 Docker 镜像。
- 当前生产 Compose 没有映射 `SQLITE_DRIVER` / `SQLITE_JOURNAL_MODE`；仅在宿主机 `.env` 添加这两项不会自动传进容器，须显式增加容器环境变量。
- 镜像从目标提交的干净检出或只含受版本管理文件的构建目录生成。`.gitignore` 不控制 Docker 构建上下文；当前 `.dockerignore` 已排除 `tmp/`、`.market-imports/`、`storage/`、`.env*` 及常见数据库文件，额外命名或位置的备份仍须核对实际排除规则，避免业务数据进入镜像。
- 不使用删除命名卷的方式重建；保留原 Compose 项目名与卷映射，避免误创建另一组空卷。若需要清理文件，由用户按项目约定处理，不能批量删除。

#### WAL 生产 Compose 覆盖示例

在目标 Linux/Node/架构完成副本和原生模块验收后，再使用此配置。它是部署配置示例，仓库中的生产 Compose 默认值尚未改变。将以下内容保存为独立部署文件 `compose.wal.override.yaml`，镜像变量使用包含目标提交的标签，发布时记录不可变摘要：

~~~yaml
services:
  app:
    image: ${APP_IMAGE:?请设置包含目标提交的镜像}
    environment:
      SQLITE_DRIVER: better-sqlite3
      SQLITE_JOURNAL_MODE: wal
    command: ["./node_modules/.bin/next", "start", "--hostname", "0.0.0.0"]
~~~

生产顺序为：准备/验证新镜像 → 停止旧服务及 worker → 备份 → 保持原日志模式完成副本演练及正式迁移 → 用新镜像的一次性诊断进程在原数据卷核对 WAL → 用覆盖配置启动服务。一次性进程应使用同一 Compose 项目、卷和环境，且覆盖 `command` 为 `node scripts/sqlite-runtime.mjs --integrity`；不启动第二个应用，不用空卷代替原生产卷。最终按第 6 节验证后再恢复使用。

在干净源码构建目录可用 `docker build -f Dockerfile.prod -t <目标镜像标签> .` 生成镜像，并用 `docker run --rm --entrypoint node <目标镜像标签> scripts/setup-sqlite-driver.mjs` 检查镜像内原生模块。部署时同时指定 `-f compose.prod.yaml -f <覆盖文件路径>`，先运行 `docker compose ... config --quiet` 检查配置，再按上述顺序执行一次性命令及 `up -d`；镜像自检不挂正式数据卷。保留原项目名，覆盖文件、镜像配置和卷路径都纳入部署记录。

## 6. 升级验收

先在演练副本执行，再对正式实例进行只读核对：

- SQLite `PRAGMA integrity_check` 为 `ok`，`PRAGMA foreign_key_check` 无记录；使用 Prisma 迁移的安装没有未完成或失败迁移。WAL 实例须核对应用实际连接的 SQLite `3.51.3`、`wal` 及所选同步级别（默认 FULL=2，显式 NORMAL=1）；迁移历史核对在前述保持原日志模式的离线维护阶段完成。
- 原行情根数、起止时间和已有源序号保留；自动同步关闭期间不能将额外追加误认为迁移结果。
- 旧会话及已归档会话可查，账户权益、持仓、当前成交、交易理由、Setup 和复盘备注对应正确；一个独立会话只显示一份正确结果。
- 浏览器刷新后，在副本或隔离验收会话验证播放、下一根、暂停立即平仓、跨非交易时段推进、秒线显示高周期、日期快进、手动平移不跳回、会话切换、图表标记与日志、Excel/PDF；实盘重演额外验证回退预览/取消/确认及 worker。不要在用户原交易上试验撤销或删除。
- 策略清单、训练关卡的读取/保存和下单快照可用；已有会话数据按迁移规则保留。
- 对 WAL 目标环境补充长时间播放、自动 checkpoint、独立 worker 与跨进程锁、异常退出后恢复验证；本机短时基准不能替代目标磁盘和镜像验收。
- 生产 start 页面/API 正常，错误日志无缺表、缺列、密钥解密失败和 worker 文件缺失；报告最终提交、迁移方式、备份位置、验收结果及未完成项。

`scripts/verify-replay-migration.mjs` 是开发时的专项核对脚本，硬编码读取本机 `tmp/replay-migration-baseline.json` 与 `prisma/dev.db`。它不是可直接移植的通用升级命令；另一台机器通常没有这个临时基线，不能将执行失败当作数据损坏，或将未执行当作已经验证。

不使用 computer use 进行本次升级验收；通过 CLI、隔离测试和只读 API 核对，实际界面由用户试用。不要把开发文档中的旧验收结果当成目标机器已经完成验收。

## 7. 回退

空仓快速推进版本将延迟计算描述写入既有 `ReplayContextRun.context` 字符串，不新增表结构。使用后回退至不识别 `FLAT_ADVANCE_V1` 的旧代码，需要匹配备份或先展开为旧格式的上下文，不能直接沿用新记录进行纠错重演。详见[空仓快速推进与回退兼容](../replay/flat-replay-advance.md#纠错上下文与回退兼容)。

先区分日志模式回退与数据库结构回退：

- **仅停用 WAL，保留本次新增交易：** 停止服务和 worker，备份当前数据；在独立维护进程显式设置 `SQLITE_DRIVER=better-sqlite3`、`SQLITE_JOURNAL_MODE=delete`、`SQLITE_SYNCHRONOUS=FULL`，运行 `db:runtime --integrity` 离线转为 DELETE，确认完整性和外键正常。随后将正式配置改为 `SQLITE_DRIVER=native`、`SQLITE_JOURNAL_MODE=delete`、`SQLITE_SYNCHRONOUS=FULL`，清除启动环境中的临时覆盖，再重启兼容当前表结构的代码。不能直接用 native 打开 WAL 库；应用会拒绝该组合。不要手动删除 WAL/SHM，也不要用升级前备份覆盖试用后新增交易。
- **回退代码或结构迁移：** 停止新服务，保留失败日志与升级后的数据库副本；先核实旧代码与当前表结构是否兼容。需要恢复时，使用匹配的旧代码/镜像、升级前一致性数据库备份、环境变量、原密钥及必要文件，再启动旧服务。恢复的备份若仍为 WAL，也须使用可用的新驱动离线转为 DELETE 后才能交给旧 native 引擎。不能只退代码继续读取不兼容的新结构数据库。

恢复升级前备份会舍弃升级之后的新写入，因此正式开放写入前先完成核对。回退涉及替换现有数据时，明确恢复点和受影响内容，不自动覆盖用户新增交易。
